## 1. 依据、目标与成功标准

有效依据依次为本次真人批准指令、《批准计划》《讨论确认与初始化交接》及课设原 DOCX。课设硬要求不能由产品设计删减。原始授权位于聊天 `01a15487-759c-7063-b6e3-78a9d9db038c` / local，turn `01a154c0-b9ef-7782-b856-c91b8c765a36`，human message `01a154c0-badb-7471-a690-b85ef34b89cb`，正文以 `PLEASE IMPLEMENT THIS PLAN:` 开头并全文引用计划；P00 已只读核实。

用户需要在食堂实际购买、记录并调整三餐，同时完成 C++ 面向对象课设。目标是在 **2026-10-28 汇报前**交付可在红米 K90 Pro Max 上使用的微信小程序、同核心 C++ 原生实验程序、源码、可重复算法对比、营养依据和演示素材。首批只覆盖一个食堂内覆盖三餐的代表性窗口，后续通过菜单包扩展。高分是目标，最终成绩由课程评定，不能提前承诺。

开发、调试和测试由 AI 完成；用户负责本人账号注册、提供真实菜单以及设备体验反馈。朋友小范围试用保留实际反馈。PPT 后续由用户使用反重力制作，本轮只规划素材。

课设评分：算法设计与分析 60 分、工程实现 20 分、表达与答辩 20 分。必须手写至少三个核心算法，分析时间/空间复杂度并做优化对比；代码现场可运行、分文件、类名大驼峰、函数与变量风格统一，关键逻辑有注释且注释率不低于 20%；输入合法性校验，异常须抛出并处理；检查内存泄漏和编译 warning。展示约 5 分钟，另需回答提问。

## 3. 购买、推荐与记录规则

1. 先按对应早餐/午餐/晚餐供应生成各窗口内合法一餐，再组合全天；不能用午餐菜单填早餐。窗口锁定和菜品锁定必须进入求解输入。
2. 自选菜汇总单道真实价格；套餐按真实总价、可选数量和米饭包含规则计算，不重复收米饭费，不把套餐价拆成虚构单菜价。售卖单位与米饭半份规则由菜单数据表达。
3. 硬约束为餐次供应、窗口、售罄、套餐、份量及显式锁定；营养偏差可解释。可选预算的主方案不隐性超支；预算内无法达到营养目标时，同时展示预算内方案与醒目标注加价的备选；预算内连合法组合都没有时明确无解。
4. 三个算法共用评分规则。先比较营养目标满足程度，再比较口味和价格；三套方案的策略差异需要显示。评分权重、并列排序、去重规则和搜索限制由 T01 冻结，当前未指定数值。
5. 推荐不等于已吃。一键确认产生摄入记录；修改、撤销只改变对应实际记录和汇总。调整推荐不能覆盖已吃快照；补记食物参与剩余餐次重算。
6. 本地保存档案、菜单与记录，导出由用户主动操作。导入校验完整后替换；失败保留当前可用数据。恢复结果需与导出前核对，不能以导出文件存在作为恢复通过。


### 3.1 营养未知与估算的统一处理（用户已确认）

- 有参考来源、实际售卖份量假定、单位及估算标识的能量/蛋白质/脂肪/碳水数据，可以参与自动推荐；估算不改写成实测。
- 上述四项任一仍未知的菜，不作为算法自动新增的候选；允许用户手动选择、锁定和记录。手动选入后作为固定内容保留，其他菜仍按同一规则求解，整体营养结果标记不完整，不承诺达标。不能为得到三套方案补造数值。
- 已吃食物含未知项时，按营养素分别显示已知小计及“不完整”；已知为零与未知分开。剩余餐次可参考已知摄入和既有餐次目标生成，但明确这是不完整数据下的参考方案，不把未知按零计入完整总量，不据此自动加大补偿或宣称全天目标满足。
- 无足够信息的自动候选时，明确提示“营养数据不足”，保留手动选餐/记餐入口；与购买规则无解、搜索限额分别表达。T01固定状态与算例，T03补可追溯估算。

### 3.2 全天预算与实际消费

- 可选预算指所选业务日期的全天总预算，以整数分记录；未设置表示不施加预算约束，零预算与未设置不同。推荐价格仅用于计划，确认后才计入实际支出。
- 菜单餐默认带入所确认份量的购买价，用户可修正实付；补记食物价格允许未知。实际支出只汇总当前有效记录，重复确认不重复入账，修改/撤销同步重算。
- 已知价格完整时，剩余可用预算=全天预算−当天实际支出；后续主方案总价不得超过此余额。已超预算或余额买不到合法余餐时，保留真实记录并明确预算内无解，不隐性提高预算或自动取消后续餐次；可查看单独标明总额及超额的备选，须由用户明确选择或调整预算。
- 有实际记录价格未知时，显示“已知支出小计、预算核算不完整”，提示补价；可以展示参考方案，但不能声称全天预算内或把未知当零。取消预算、改价和改撤记录后，使用当前有效数据重新计算。

### 3.3 日期、餐次、售罄与锁定状态

| 情境 | 规则与可观察反馈 |
|---|---|
| 进入/跨日 | 今天按设备本地日期确定，记录保存明确业务日期和当时日期偏移信息；启动/回到前台时检查日期变化。跨日新建今天的计划，不迁移昨天的摄入、锁定或售罄。系统时钟与时区变动不重写历史日期 |
| 餐次待处理 | 餐次按业务日期分别记录待处理、已确认或用户明确结束。没有固定时间自动认定“已经吃过”；时间已晚仍可补记、选择待规划餐次或结束该餐，界面不把过去餐次冒称当前供应 |
| 已确认/结束 | 已确认餐的实际快照锁定；已结束未记餐不会虚构摄入，也不自动补推该餐。用户可重开该餐或补记/改撤；撤销该餐全部有效记录后回到待处理，再由用户选择是否结束 |
| 临时售罄 | 标记作用于业务日期+窗口+餐次+稳定菜品标识，可手动解除；到下一业务日期不继承。售罄更新后重算未吃餐，历史摄入不变 |
| 锁定失效 | 被锁菜售罄、停售或菜单更新后不可购买时，保留已吃快照；未吃的失效锁定明确提示，等待用户解除/替换或取消本次更新。不能静默去锁或违反供应规则；解决前不得返回假合法方案 |
| 菜单更新 | 导入通过结构及语义校验后，先提示对当前未吃计划/锁定的影响；用户确认后原子替换并使旧计划失效。取消或失败保留原菜单与计划；新计划必须标明新菜单版本 |

## 4. 营养规则与待冻结项

本节复述批准计划的产品规则，适用于成年学生日常饮食管理，输出为估算；不构成医学处方。本轮未重新研究外部资料，所列链接是批准计划提供的依据入口，后续 T01/P09 需独立核验适用条件和计算。

| 规则 | 当前决定 | 后续必须核实 |
|---|---|---|
| 静息能量 | 采用 Mifflin–St Jeor，再结合活动水平估算消耗 | 公式各项、单位、输入条件、边界样例及来源适用性 |
| 维持/减脂 | 维持以估算消耗为起点；减脂缺口为估算消耗的 10%，最多 300 kcal/日 | 这是产品初始参数，须标记可校正；不写成指南统一处方 |

## 5. 技术、数据和算法草案

已选架构为原生微信小程序 TypeScript＋WXML/WXSS、C++17 算法核心及 WebAssembly 桥，同一 C++ 核心同时供本机命令行实验程序调用。当前没有代码、可用工具链证明或 WASM 结果。

### 数据边界草案

统一版本化 JSON，金额使用整数分，能量标 kcal，主要营养素标 g，档案使用明确单位；份量按实际售卖单位，米饭可半份。具体字段名、必填项、枚举、精度和迁移策略尚未冻结；第3节补充的业务语义是T01必须实现的约束，不能作为自由解释项。

| 对象 | 最少语义要求 |
|---|---|
| Profile | 计算所需身体档案、活动、目标、口味；专业目标及适用性信息；体脂率选填 |
| MenuCatalog | 菜单版本，食堂/窗口/餐次，菜品和套餐规则，价格、份量、营养来源/假定/未知状态 |
| PlanRequest | 业务日期、待规划餐次、菜单/目标/配置版本、可选全天预算、实际记录及其完整性、偏好、窗口/菜品锁定、算法与请求标识 |
| PlanResult | 请求标识与输入版本、推荐组合、已知汇总及完整性、全天/剩余预算说明、差异与求解状态、三种取舍；未知、估算、截断与超时分别表达 |
| MealLog | 稳定记录标识、业务日期/餐次、实际份量/实付金额及未知状态、营养和菜单快照、修改/撤销关联；菜单外食物可手录 |

C++ 提供统一规划入口，统一输入、评分与输出语义。WASM 返回数据所有权、复制时机和释放方式必须书面明确并验证；原生异常不能直接越过桥而不可见。错误状态须区分非法输入、无可行组合和资源限制，具体枚举在 T01 确定。只在外部输入边界做必要校验，不以吞错、空结果或默认值伪装成功。

### 三个手写核心算法

| 算法 | 任务 | 验证重点 |
|---|---|---|
| 贪心 | 快速基础组合、对比基线 | 合法性、确定性、质量差距；不保证最优 |
| 动态规划 | 按餐次组合候选并复用等价状态 | 状态定义、等价条件、离散化及是否损失精度；不能未经证明标全局最优 |
| 分支限界 | 界限剪枝搜索 | 界限正确性、剪枝不漏解；在小规模完整搜索时对照穷举 |

BMI 和能量公式不计入三个算法。复杂度应从最终实现的候选规模、状态维度和剪枝策略推导，本 PRD 不提前填写未经实现的复杂度结论。完整穷举用作独立小规模参照，不能复用被测剪枝逻辑作为“独立”参照。独立验证分两层：先从可人工列全的极小原始菜单核对合法单餐候选的完整性、半份米饭及套餐计价，再以独立全天穷举核对评分和搜索结果；不能只在生产候选表上穷举而声称覆盖候选生成。候选预筛选、离散化或截断造成的精度损失也必须纳入近似标记。实验同菜单、目标、约束、评分与计时口径，记录结果质量、耗时、状态/节点量、输入版本、工具/设备和可复现运行方式；不预设某算法必胜。搜索上限触发时不得伪称精确最优。

## 6. 最早技术门禁与模块协作

模块职责草案：DSH 管 C++ 核心、营养公式/目标与适用性校验的唯一计算实现、原生实验及 C++ 导出侧；反重力管小程序界面、本地数据、菜单处理及小程序桥接侧；P01 负责共用契约、构建接合与集成版本，P09 只独立核验。具体文件归属在 T01 冻结，本轮不创建代码目录、分支或候选。共享契约由 P01 单一协调，跨模块变更先同步契约版本再集成；外部 Agent 同目录接入不代表可同时覆盖共享文件。


### 6.1 支持规模、响应与超限

T01冻结逻辑规模维度（各餐窗口/菜品数、单餐候选、套餐展开、DP状态及搜索节点）、规模分组与测量方案，不凭空填写已经达成的性能数字。T02以红米最小链路取得初测，P01会同DSH/反重力据此写入版本化性能验收配置：各规模上限、端到端响应目标、测量起止点、重复次数、统计口径和资源限制；T07用完整三算法复测并在T08前冻结。初测不代表完整规模通过；若目标不满足，应先整改，变更范围或明显降低体验目标须交用户决定。

求解期间显示加载与当前输入状态；输入变化后旧请求结果不覆盖新请求。达到规模/时间/状态限额时，若已有合法方案则返回并标近似、限制原因及未证明最优；没有合法方案则明确资源限制，不能宣称“已证明无解”。首版支持规模与实测响应条件未冻结/未验证，A10不可判通过。原生与真机、算法耗时与页面端到端耗时分别记录。
