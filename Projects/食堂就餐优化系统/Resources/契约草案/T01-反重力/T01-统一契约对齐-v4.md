## 3. 四大核心维度的深入对齐分析

### 3.1 目标、适用性和页面状态
- **核心契约要求**：`TargetResult.status` 包含 7 种明确状态（`Ok`、`REFERENCE_ONLY`、`TARGET_REVIEW_REQUIRED`、`TARGET_COMPOSITION_CONFLICT`、`MANUAL_TARGET_INCONSISTENT`、`MANUAL_TARGET_INCOMPLETE`、`AUTO_TARGET_DISABLED`）。
- **页面映射保证**：
  1. 仅当 `status === 'Ok'` 且 `applicability.eligible === true` 时，前端才将目标标记为“有效自动目标”，并允许触发全自动配餐；
  2. 遇到 `AUTO_TARGET_DISABLED`（未成年、超龄、孕哺、疾病饮食）、`REFERENCE_ONLY`（过轻维持）、`TARGET_REVIEW_REQUIRED`（低能量）等状态时，前端界面坚决**不显示为有效自动目标**；
  3. 若 `TargetResult` 包含 `computed` 结构，仅作为“当前参考计算值”展示并明确注明“不可用于自动规划”；
  4. 当 `PlanDay` 返回 `status: "TargetUnavailable"` 时，`plans` 为空数组，前端将 `targetStatus` 转化为友好的业务阻断提示（例如：“当前健康状况暂不支持自动配餐，建议遵循医生/营养师指导”），杜绝将其误显为 `OkPartial`（普通部分营养缺失）或算法求解失败。

### 3.2 手动目标存储与应用
- **核心契约要求**：
  - 手动目标分为“存储存证（`stored`）”与“自动规划应用（`applied`）”两个独立状态；
  - 必须提供 `sourceType: "professional" | "userEntered"`，可选 `sourceNote`；
  - 核心执行能量与 4/9/4 宏量换算容差检查（`max(20 kcal, 2%)`），超容差置 `MANUAL_TARGET_INCONSISTENT`；
  - 缺少宏量若有派生必须记录于 `derivedFields[]`，无明确规则置 `MANUAL_TARGET_INCOMPLETE`；
  - 手动输入绝不能绕过适用人群、过轻拦截、能量下限与宏量门槛。
- **页面与存储实现保证**：
  1. 小程序个人档案表单新增 `sourceType` 单选按钮与 `sourceNote` 文本框，录入直观便捷；
  2. 本地 `wx.setStorageSync` 存储的 `Profile.goal.manualTargets` 完整保存用户声明的原始值（`energyKcal`、`proteinDg`、`fatDg`、`carbDg`、`sourceType`、`sourceNote`）；
  3. 即使因超容差或适用性不满足导致 `applied === false`，本地依然保留该条专业/用户存证记录，供用户随时查看；
  4. 绝不将系统派生的宏量字段覆盖到用户原始录入项中，而是通过 `derivedFields[]` 显式标出，保证数据溯源清晰。

### 3.3 配置版本、缓存和 WASM 交互
- **核心契约要求**：
  - 请求必须携带 `nutritionConfig` 完整快照，包含 `version: "nutrition-v1.1-candidate"`、`hash` 及各配置节点；
  - 缓存依据 `profile.revision` 与 `nutritionConfig.version` 进行失效判定；
  - 导出接口为 `mp_plan`、`mp_nutrition_target`、`mp_validate_menu`、`mp_alloc`、`mp_free`、`mp_api_version`、`mp_contract_version`。
- **页面与运行时保证**：
  1. 小程序将 `nutrition-v1.1-candidate.json` 作为本地静态配置资产打包，发起调用时直接作为 JSON 节点附着在快照中；
  2. 本地缓存键定义为 `cache_${profile.profileId}_r${profile.revision}_cfg${nutritionConfig.version}_m${catalog.menuVersion}`，配置或档案一旦变动，历史缓存天然隔离并失效；
  3. WASM C ABI 接口与内存释放机制（JS 申请输入缓冲区并在 `finally` 释放，C++ 返回输出缓冲区并在 JS 拷贝后立即释放）与 v1 完全一致，无任何新增或变更的导出符号，无调用端阻碍。

### 3.4 18 岁碳水门槛与补充裁定一致性
- **核心契约要求**：
  - 按照 P01 补充裁定（`2026-10-20-t01-age18-clarification-v1`），18 岁分支保持当前 v1.1 候选行为，配置 `carbFloorGPerDay = null`，不另设独立 130g/day 碳水检查；
  - 18 岁自动目标仍受女性 1200 / 男性 1500 kcal/day 能量下限、4–18 岁宏量比例（碳水 45–65%、蛋白质 10–30%、脂肪 25–35%）和 4/9/4 一致性严格约束。
- **页面端处理保证**：
  1. 页面表单与前端逻辑不编写任何独立的 130g 硬校验，完全遵循 C++ 核心在 WASM 层返回的计算结果；
  2. UI 界面绝不向用户表述“18 岁不需要 130g 碳水”或“130g 不安全”，而是展示由系统综合校验的宏量合理区间；
  3. 针对 18 岁用户，界面规范展示 `AGE_18_EXTRAPOLATION` 外推提示标签，客观合规。

## 4. 实现阻塞差异逐项核对

经对小程序页面层、存储层及 WASM 桥接层的全方位审查：

1. **旧映射位置对照**：旧提案及 v2 报告中的字段映射表已涵盖了本次 v1.1 的主体结构，本次 v1.1 仅在 `TargetResult`、`Profile.goal.manualTargets` 和 `PlanResult.status`（新增 `TargetUnavailable`）上做了精确的结构化收敛。
2. **候选字段与状态核查**：所有新增字段（如 `sourceType`、`sourceNote`、`derivedFields`、`reasons`、`composition`）均为标准的字符串、数组或整数对象，在微信小程序原生 TypeScript/JavaScript 环境下均有原生类型支持，无需第三方特殊库。
3. **存储与生命周期**：本地 Storage（`wx.setStorageSync` / `wx.getStorageSync`）对完整快照与日志历史有充足的存储空间和高效的读写性能；幂等键（`confirmationId`）与稳定记录 ID（`recordId`）机制完全不受营养配置收口影响。
4. **WASM 交互**：WXWebAssembly 环境内存分配与 C ABI 调用无任何变化。

**核查结论**：
> **页面/调用/存储可按 v1.1 候选接入，未发现实现阻塞差异。**
