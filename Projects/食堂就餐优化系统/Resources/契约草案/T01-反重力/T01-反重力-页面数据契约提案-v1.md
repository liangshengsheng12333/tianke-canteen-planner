## 1. 业务语义与页面设计原则（PRD 落实）

本提案严格落实主 PRD v0.2（尤其是第 2、3、5、6 节）确立的刚性业务语义，页面交互与数据层设计遵守以下不可妥协原则：

1. **推荐与实吃严格解耦**：
   - 算法推荐的方案是计算核心输出的建议搭配，不等于用户实际摄入。
   - 只有用户在小程序界面点击“确认实吃”动作，才产生有效实际摄入记录（`MealLog`）。
   - 确认实吃必须具备**操作幂等性**，同一餐次重复点击不能重复累计营养和支出；修改或撤销仅影响对应 `MealLog` 状态。
   - 调整未吃餐次的推荐方案绝不能覆盖或篡改已吃记录的历史快照。
2. **“已知为零”与“未知（Unknown）”严格分离**：
   - 营养素或价格数据缺失必须明确表达为 `null`（未知），严禁填充默认值 `0`。
   - 依据 PRD 3.1 规则：菜品的能量、蛋白质、脂肪、碳水四项中若有任意一项未知，算法核心绝不能将其作为自动新增的候选菜品；但允许用户在 UI 手动选入、锁定或补记。
   - 包含未知项的方案或实吃记录，其汇总结果必须强制携带 `isComplete: false` 标记，界面展示“已知小计 + 营养不完整提示”，不得声称目标已满足。
3. **全天预算与实付金额控制**：
   - 全天预算为整数分（cents）。未设置预算（`null`）与预算为零（`0`）属于不同业务状态。
   - 计划价格仅供参考，实际支出按用户实付（或确认时的菜单快照价）结算。
   - 若实际记录中包含价格未知的菜品，系统提示“已知支出小计、预算核算不完整”，禁止盲目判定超支或未超支。
   - 预算内无可行组合时，页面明确展示“预算内无解”，并支持展示加价备选（醒目标注超出金额），严禁静默超出预算。
4. **单窗口与售卖规则约束**：
   - 每餐默认限制在单个窗口内购买；支持用户优先指定锁定窗口。
   - 份量规则：**仅米饭允许半份（0.5）**，其他菜品均为整份（1.0）。
   - 套餐规则：套餐为原子总价，严格按套餐总价与规则校验，UI 不得将套餐拆解为虚构单菜价。
5. **本地生命周期与状态作用域**：
   - 业务日期（`businessDate`）：严格遵循设备本地自然日（`YYYY-MM-DD`），包含本地时区偏移。
   - 跨日处理：每次小程序冷启动或从后台唤醒切至前台，检测业务日期；跨日自动生成新一天的规划上下文，不迁移昨天的摄入记录、临时锁定或售罄状态。
   - 临时售罄（SoldOut）：作用域为 `业务日期 + 窗口ID + 餐次 + 菜品ID`，仅限当日有效，支持手动解除；次日自动清空。
   - 锁定失效：当被锁定的菜品标记售罄、停售或菜单更新下架时，保留已吃快照；未吃计划明确提示“锁定失效，请调整”，等待用户交互，禁止静默丢弃锁定或输出假合法方案。

## 2. 建议数据契约定义（TypeScript 规范提案）

为方便反重力（小程序 TS/JS）与 DSH（C++ 结构体 / WASM 导出层）进行无歧义对接，建议统一采用以下数据结构定义（待 P01 审定并冻结为共享契约）：

### 2.1 基础枚举与单位

```typescript
// 基础餐次枚举
export type MealType = 'breakfast' | 'lunch' | 'dinner';

// 算法策略枚举
export type StrategyType = 'primary' | 'budget_saving' | 'taste_first';

// 求解器返回状态枚举
export type SolveStatusCode = 
  | 'SUCCESS'                 // 求解成功，方案完整
  | 'PARTIAL_NUTRITION'       // 求解成功，但含估算或未知营养项（结果不完整）
  | 'NO_FEASIBLE_SOLUTION'    // 硬约束下无可行解（窗口/餐次/售罄/不可拆规则限制）
  | 'BUDGET_EXCEEDED'         // 预算内无合法解，提供超额备选方案
  | 'TIMEOUT_APPROXIMATE'     // 计算超限/超时，返回近似贪心解
  | 'INPUT_INVALID'           // 入参结构或业务逻辑校验失败
  | 'CORE_EXCEPTION';         // C++ 计算核心内部抛出异常

// 记餐状态枚举
export type MealLogStatus = 'CONFIRMED' | 'REVOKED' | 'SKIPPED';
```

**单位与精度规范**：
- **金额**：严格为**整数分**（`cents: number`，例如 15.50 元表示为 `1550`）。
- **能量**：严格为**整数千卡**（`kcal: number`）。
- **蛋白质 / 脂肪 / 碳水化合物**：建议传输为**保留 1 位小数的定点数**（克 `g`，例如 `24.5`），或定点整数**分克**（`0.1g`，如 `245`）。本提案建议在 JSON 中使用精确浮点表示（克，最多 1 位小数）。
- **份量**：数字类型，米饭支持 `1.0` 与 `0.5`，其他菜品严格为 `1.0`。

## 3. 页面流与防竞态调用机制

### 3.1 请求标识（requestId）与防旧结果覆盖机制

在真机上调用 WASM 核心计算为异步过程（WebAssembly 异步加载或主线程/Worker 计算）。当用户高频交互时（如连续切换早餐/午餐/晚餐，或快速勾选锁定菜品）：
1. 页面维护一个单调递增的活跃请求标识：`activeRequestId = generateUUID()`；
2. 发起计算前，在本地存储记录当前发起的 `activeRequestId` 和对应参数快照；
3. UI 立即切入 `CALCULATING` 加载状态，呈现骨架屏或半透明遮罩；
4. 当 WASM 桥返回结果时，前端比对：
   ```typescript
   if (result.requestId !== this.activeRequestId) {
     console.warn(`[Bridge] Discarding stale result for request ${result.requestId}, current active is ${this.activeRequestId}`);
     return; // 丢弃过期计算结果，防止脏旧数据覆写当前界面！
   }
   ```
5. 结果合法且版本匹配时，才更新页面展示并写入当前规划缓存。

### 3.2 典型页面业务场景与流转要求

| 场景 | 用户动作 / 触发条件 | 调用核心时机与参数 | 页面反馈与状态处理 |
|---|---|---|---|
| **S01 建档与更新** | 首次进入或修改身体数据 | 调用核心独立接口 `calculate_nutrition_target(profile)` | 校验成人与低体重；若过轻拦截减脂并给出医学提示；成功则保存 Profile |
| **S02 首页三餐展示** | 打开小程序 / 切前台 / 切换餐次 | 读取本地当餐规划缓存；若缓存过期/不存在，组装 `PlanRequest` 发送核心计算 | 优先展示主推荐（窗口、菜品、预估价格）；提供经济/口味备选入口；展示已知能量/蛋白质进度条；若有未知营养标记“数据不完整” |
| **S03 换菜与同窗调整** | 用户在某餐点击“换一道”或“换窗口” | 附带当前已锁定项与排除项，重新调用核心计算 | 保持在同一窗口内重新搜寻替代菜品；若同窗无可替换菜品，提示“当前窗口无其他满足约束菜品，建议切换窗口” |
| **S04 锁定菜品/售罄** | 用户手动锁定某菜，或打勾标记售罄 | 更新 `constraints.lockedItems` 或 `soldOutDishIds`，触发重算 | 被锁菜品作为强制约束代入；若用户锁定的菜品导致预算超限或不可行，展示超预算提示或加价备选，不静默丢弃锁定 |
| **S05 确认实吃** | 点击“确认就餐”按钮 | **不调用算法计算**；直接将当前方案（或用户勾选内容）进行深拷贝，生成 `MealLogV1` | 检查防重标记（幂等）；写入本地存储；标记当餐状态为 `CONFIRMED`；同步扣减今日剩余预算；更新今日已摄入营养仪表盘 |
| **S06 修改 / 撤销实吃** | 用户在记录页修改份量、补录价格或点击撤销 | **不调用算法计算**；直接操作更新对应 `MealLog` 状态为 `REVOKED`，或生成新版本 `MealLog` | 重新汇总今日有效摄入与实际支出；若后续餐次尚未就餐，触发后续餐次推荐方案重算 |

## 4. 本地数据存储与快照持久化设计

小程序端使用原生持久化存储 `wx.setStorageSync`，按功能严格分离命名空间（Key），杜绝大单一对象引起的存储死锁与性能抖动。

### 4.1 本地存储 Key 映射表

| 存储 Key | 数据结构 | 作用域与生命周期 | 说明 |
|---|---|---|---|
| `storage:user:profile:v1` | `UserProfileV1` | 长期持久化 | 用户基本档案与身体偏好 |
| `storage:menu:active:v1` | `MenuCatalogV1` | 跨日持久化（直到被新版本覆盖） | 当前正在使用的有效菜单与窗口数据 |
| `storage:menu:meta:list` | `Array<{ catalogId, version, name }>` | 长期持久化 | 本地已导入的菜单包元数据版本列表 |
| `storage:plan:cache:{date}:{meal}` | `PlanResultV1` | 当日单餐有效，跨日自动失效 | 尚未确认就餐的推荐候选缓存 |
| `storage:meal_logs:{date}` | `MealLogV1[]` | **永久历史记录，不可篡改** | 当日实际记餐流水日志（含快照） |
| `storage:daily_state:{date}` | `{ soldOutDishIds, lockedWindowId, lockedItems }` | 仅当日有效，跨日清空 | 当日临时的售罄标记与用户锁定标记 |

### 4.2 快照独立性保障（防止未来菜单变更影响历史）

- **痛点**：若记录仅保存 `dishId: "dish_001"`，当两个月后新学期菜单调整（如价格从 12 元涨到 14 元，或份量发生变化），历史饮食记录与统计将全部失真。
- **规范**：在写入 `MealLogV1` 时，反重力页面逻辑执行**深拷贝快照**：
  - 复制菜品名称 `dishName`；
  - 复制结算时的实际单价 `priceCents`；
  - 复制当时的营养数值 `energyKcal`, `proteinG`, `fatG`, `carbsG`；
  - 记录当时菜单版本号 `catalogVersion`。
- **效果**：无论未来菜单如何升级换代、删除菜品，历史记餐记录与当日营养分析完全自包含、不可变。

## 5. 预算、价格与套餐处理规则

1. **整数分结算与运算**：
   - 界面所有价格输入、存储、加减均以“分”为单位，仅在最终渲染 UI 时格式化输出为元（例如 `(cents / 100).toFixed(2)`）。
2. **全天预算扣减流水线**：
   - 当日已吃有效记录的总支出：
     $$\text{todaySpentCents} = \sum_{log \in ValidMealLogs} log.actualTotalCostCents$$
   - 当所有已吃项均具备确知价格时：
     $$\text{remainingBudgetCents} = \text{dailyBudgetCents} - \text{todaySpentCents}$$
   - 若存在价格为 `null` 的实吃项：
     - `isSpentComplete = false`；
     - `remainingBudgetCents = null`；
     - 界面醒目显示：“已记录已知支出 ￥25.00，部分食物价格未知，剩余预算不完整”。
3. **套餐原子性保证**：
   - 核心输出方案如果包含套餐，`items` 中明确标记 `isComboItem: true` 和 `comboId`。
   - 套餐的总价格严格从 `combo.totalPriceCents` 计入，绝不在前端拆分成“大荤 8 元 + 素菜 4 元”。
4. **半份米饭结算**：
   - 米饭半份价格由菜单数据中显式指定的 `halfPriceCents` 决定（若无显式指定，按 `Math.round(priceCents / 2)` 由 C++ 计算核心统一决定并输出），禁止前端自行猜测计算。

## 6. WASM 桥调用规范与错误边界（反重力侧诉求）

为保障小程序真机（如红米 K90 Pro Max）运行稳定、内存不泄漏、异常不黑屏，反重力对 C++ / WASM 导出层提出如下接口与错误边界诉求：

### 6.1 导出函数与内存管理约定建议

```cpp
// 导出给 WASM 的 C 接口签名建议 (由 DSH 在 C++ 侧实现)
extern "C" {
  // 1. 核心规划计算接口
  // 入参：PlanRequestV1 的 JSON 字符串指针 (UTF-8)
  // 返回：PlanResultV1 的 JSON 字符串指针 (分配在 WASM 堆上)
  const char* SolveMealPlan(const char* request_json_ptr);

  // 2. 内存释放接口 (必须提供，防止 JS 端无法释放 C++ malloc/new 出来的字符串内存)
  void FreeMealPlanResult(const char* result_ptr);

  // 3. 营养目标与适用性计算接口 (建档时独立调用)
  // 入参：UserProfileV1 的 JSON 字符串指针 (UTF-8)
  // 返回：包含目标与适用性检查结果的 JSON 字符串指针
  const char* EvaluateProfileTarget(const char* profile_json_ptr);
  void FreeProfileTargetResult(const char* target_ptr);
}
```

### 6.2 JS 侧安全调用封装模板

```typescript
// miniprogram/src/services/bridge/wasm_bridge.ts 建议模式
export async function invokePlanSolver(request: PlanRequestV1): Promise<PlanResultV1> {
  const requestJson = JSON.stringify(request);
  let resultPtr: number = 0;
  
  try {
    // 1. 将字符串写入 WASM 堆
    const reqPtr = allocateUtf8String(requestJson);
    
    // 2. 调用 C++ 导出函数
    resultPtr = wasmModule._SolveMealPlan(reqPtr);
    
    // 释放请求字符串
    wasmModule._free(reqPtr);
    
    // 3. 从 WASM 堆读取返回的 JSON 字符串并解析
    const resultJson = readUtf8String(resultPtr);
    const parsedResult: PlanResultV1 = JSON.parse(resultJson);
    return parsedResult;
  } catch (error) {
    console.error("[Bridge Exception]", error);
    // 封装为符合契约的错误对象，绝不让底层异常导致前端崩溃
    return {
      requestId: request.requestId,
      catalogVersion: request.catalogVersion,
      statusCode: 'CORE_EXCEPTION',
      statusMessage: `计算引擎异常: ${error instanceof Error ? error.message : String(error)}`,
      solutions: [],
      metrics: { elapsedMs: 0, algorithmUsed: 'none', statesEvaluated: 0 }
    };
  } finally {
    // 4. 确保在 finally 中释放返回结果内存！
    if (resultPtr !== 0) {
      wasmModule._FreeMealPlanResult(resultPtr);
    }
  }
}
```

### 6.3 异常边界要求
- C++ 核心代码在处理非法 JSON、空菜单或极端约束时，**必须在 C++ 内部使用 `try ... catch` 捕获异常**，并将其序列化为 `statusCode: "INPUT_INVALID"` 或 `"CORE_EXCEPTION"` 的合法 JSON 返回。
- 绝不能让 C++ 原生未捕获异常越过 WASM 边界，导致小程序 WASM 运行时终止（Abort）或崩溃闪退。

## 9. 待 P01 与 DSH 协作确认项清单

为确保后续 T01 顺利冻结并解锁 T02 / T04 / T05，提出以下待接合与决策项：

1. **WASM 传输协议格式确认（P01 / DSH）**：
   - 反重力建议：在 T01 和 T02 初测阶段，严格采用 **UTF-8 JSON 字符串** 通过 WASM 堆指针传递；格式直观、易于打桩排错。待 T07 遇到明显序列化瓶颈时再评估二进制编码。DSH 是否同意此输入输出格式？
2. **内存所有权与释放职责（DSH 确认）**：
   - 建议在 C++ 端提供显式的 `FreeMealPlanResult(const char*)` 导出函数，由 JS 侧在 `finally` 块中调用释放。DSH 是否支持该模式，或者有其他生命周期管理机制？
