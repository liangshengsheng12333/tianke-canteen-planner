## 3. 本轮实现目标

在同一份 C++17 共享核心中实现一个真实、手写、可运行的贪心基线：读取一份明确标注“模拟”的最小合法菜单与目标/规划输入，按 v1.2 契约实际计算并产出选餐结果。结果必须由 C++ 核心运行产生；静态 JSON、写死的选餐答案、JavaScript 替代算法都不算实现。

同一核心应可被原生 CLI 和 WASM 导出调用。按候选实际规定实现本链路需要的目标/适用性及计划逻辑、字段单位、合法性、排序、业务状态和错误边界。贪心算法不是完整三算法交付，不宣称最优；按契约设置或报告搜索/规模限制，不把限额造成的结果说成穷尽证明。

T01 配对样例文件含 9 组 ComputeNutritionTarget 输入/期望结果。使用原文件、不改夹具，验证已实现的该 API 与 9 组样例的实际输出；逐例记录通过、不支持或失败。另构造一份小型 PlanDay 模拟输入，使其使用同一核心可算出的有效目标并返回真实选餐结果。至少再验证一个契约定义的输入错误，以及一个契约定义的无可用方案/目标不可用结果，按实际契约区分 INVALID_INPUT、NoFeasible、NutritionDataInsufficient、ResourceLimited、TargetUnavailable 等语义。不得把资源限额说成已证明无解。若本子交付未实现某个样例或状态，明确列出，不伪造通过。

如果调用方请求的 API、算法、策略或契约行为本轮不实现，只能返回 T01 明确允许的错误/状态；不得新造 NOT_IMPLEMENTED 等错误码、伪造成功或默默降级。若 T01 没有表达某个必要的“不支持”边界，暂停该分支并把具体字段、触发输入、缺少的契约状态和建议决策交 P01；不得自行改共享契约。

最小示例要符合 v1.2：contractVersion=1.0；整数单位与输入范围；合法稳定 ID；完整 nutritionConfig 快照和实际 canonical hash 口径；target/applicability 与 PlanResult 的状态语义。营养未知使用 null 而非 0；自动候选不得利用未知营养伪装完整。手动存证与应用分离，风险/不适用、过轻、能量下限和宏量状态按契约返回，不得由手动目标绕过。18 岁 carbFloorGPerDay=null 时不另做 130g/day 检查，但其他能量下限、宏量比例、适用性和 4/9/4 规则仍适用。v1.2 的 energyFloor 在 nutritionConfig 顶层；配置快照 hash 按契约排除自身根 hash 后规范化计算，不用 JSON 文件原始字节哈希冒充。
