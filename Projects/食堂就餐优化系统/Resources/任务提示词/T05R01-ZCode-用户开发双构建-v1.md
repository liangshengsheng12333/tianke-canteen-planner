## 目标：两个构建，一套业务

增加清楚、可复现的最小构建配置/脚本，生成隔离的 `user` 和 `dev` 两个项目输出；旧输出若存在，不清空或覆盖，改用本任务唯一新目录/新版本输出，若目标目录已存在则先查身份并另选新目录。

**user 构建保留**：三算法、推荐与自选、记录/确认/改撤/补记、月历历史、档案与预算、简易/完整营养展示、浅色/深色/跟随系统、官方菜单升级、首次可跳过和可重看的四步教程、普通文件备份/恢复及必要错误提示。

**user 构建移除**：开发诊断页的 `app.json` 注册和所有可达导航/直达入口；开发专用原始 JSON/哈希、模拟夹具、故障注入、性能测试、ABI 探针等页面/数据/入口。仅不显示按钮或 CSS 隐藏不算隔离。按依赖实际剥离纯开发文件和大夹具，不能盲删业务仍依赖的模块；不能因移除诊断页损坏普通备份/恢复和错误处理。

**dev 构建保留**：与 user 相同的业务、菜单、教程与核心，加上现有开发诊断页、模拟输入、性能/ABI检查与原始 JSON/哈希检查入口。

简易/完整是两种用户营养展示模式，不是构建或开发权限；两种构建都保留。不得加入“开发者模式”开关、隐藏连点入口、新账号/权限服务或第二套营养/规划实现。除预期的开发页、开发夹具、路由与构建元数据之外，user/dev 的共同业务源码、菜单和 WASM 核心必须同源同身份；业务响应不能因为构建类型分叉。

## 实施顺序

1. **复核输入和工具**：检查 P01 填实候选、两份前置反馈、菜单/教程状态、`miniprogram\src\app.json`、`miniprogram\project.config.json`、`pages\dev\index`、`tools\miniprogram` 现有命令与依赖关系。已知 `app.json` 当前注册 `pages/dev/index`，`project.config.json` 的 `miniprogramRoot` 指向 `src/`；`typecheck-src.mjs` 是类型检查工具，不等于用户/开发包构建器。按现场复核更新事实，不假设已有未证实的 build 命令。
2. **设计最小分支**：定义一份可读的构建配置及两种目标，按真实 import/导航/路由依赖分 user/dev 文件集合；保持共享业务实现唯一。优先生成两份隔离项目根和各自 `app.json`/项目配置，不编辑源目录删文件来凑包。开发页和纯开发夹具从 user 产物中不可达且不被打包；dev 产物保持原诊断可用。
3. **可重复生成**：新增最小构建入口，参数/默认值清楚；构建失败应返回错误而不留下伪完整包。固定排序并输出命令、版本、源候选身份、文件清单、user/dev 逐文件 SHA256/字节数和构建 manifest。不得加入通用打包框架、静默回退、猜测路径或删除旧输出的清理步骤。
4. **分别实际编译**：用当前实际微信小程序工具链分别导入/编译 user 与 dev 输出。先按现场可用入口确认编译是否成功；记录确切命令或 GUI 操作、工具版本、project root、退出/编译结果和日志。Node 类型检查通过不代表两个微信构建可编译。
5. **验证隔离与同源**：
   - user：`app.json` 无 `pages/dev/index`；从首页/我的/数据管理、可见链接和直接 `navigateTo`/路径访问都不能进入开发页；用户产物清单无开发专用页面/夹具/原始 JSON/哈希诊断资源。
   - dev：原诊断入口真实可达，原模拟输入、性能/ABI/原始 JSON 检查可用。
   - 两包核心 WASM 哈希、菜单 hash/catalogHash、共用业务源哈希一致；生成 G1 单餐/必要的相同请求，实际执行同一算法与参数，比较完整业务响应（解释构建元数据等动态字段差异）。不复制前端营养公式或另一套核心；保留测试输入、原始响应与差异清单。
   - user 用隔离存储核新装、旧官方菜单升级后热量/新版本持久化、自定义导入/历史快照保留、教程首次/跳过/重看、选餐→确认→历史、备份/恢复及简易/完整/主题；两包各自报告实际覆盖项。不得清空或覆盖真实用户数据。
6. **停止与交接**：只交本任务候选、user/dev 构建输出、manifest、依赖/入口审计、原始验证证据和唯一反馈。不要推广到生产、不替 P01 决定推广、不继续最终红米性能/P09总审；用户构建成绩不能拿 dev 构建诊断替代。

## 代码简洁约定（本单适用）

本约定适用于新构建脚本及直接改动；无关旧代码只记录，不顺手重构：

1. 在接收外部输入、文件内容或第三方响应的适当边界校验；内部已经建立的契约不逐层重复检查。
2. 内部契约被违反时保留清楚、可定位的失败信息；避免吞异常后返回空结果、默认值或假成功。
3. 重试、降级、默认值对应真实失败或明确业务要求；不为假想问题添加多层备用路径。
4. 兼容层须有已支持版本、真实调用方或明确迁移需求；不预先兼容不存在的旧格式或未来接口。
5. 在当前范围内直接实现，不为未来可能的需求增设抽象层或兜底框架。

这不禁止 try/catch、判空、重试或兼容代码；保留时说明它保护的真实条件与失败后的结果。来源为凉笙《代码简洁约定》，SHA256 `104B13661AF6851A08C70444F8A66B0BF94B02F757DAC9A079393E5497AA1A7A`。
