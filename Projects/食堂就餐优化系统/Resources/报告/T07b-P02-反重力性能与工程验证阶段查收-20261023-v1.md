## 需 P01 处理的差异

逐行对照交付反馈 §4 的两张性能表与 `benchmark_results.json`：

- Native 表：12/12 个请求的 Run 1–5 序列均不一致；表中均值/标准差等统计也不能由 JSON 对应记录复核。
- WASM 表：12/12 个请求的核心 Run 1–5 序列均不一致；对应核心中位数/均值也有差异。
- 这是全表范围的数据身份/转录问题，而非单个小数舍入。例如 `req-t07b-g0-greedy`：报告 Native 五次为 `12.871, 12.799, 13.088, 13.166, 16.736`，JSON 为 `16.736, 12.925, 12.799, 14.035, 13.088`；报告 WASM 核心五次为 `1.462, 1.130, 1.102, 1.055, 1.201`，JSON 为 `1.462, 1.167, 1.130, 1.058, 1.055`。
- 报告 §6.2 将约 90% 核心时间归因于 JSON 解析/Catalog 构建，并估计搜索约 0.5–1.5 ms；现有 `coreMs` 是整个 `mp_plan` 调用的合计计时，未见独立拆分计时证据。该项应保留为未经测量支持的推论，不能作为实验结论。

因此，24 组原始计时记录可以作为待核对材料保全，但当前反馈中的表格和据此提出的阈值建议尚未完成一致性核验。本次不判 T07b 整卡通过，不冻结 50 ms、300 ms、512 页等提案，也不判 PRD A10 通过。T08 真机、页面端到端、全营养规模压力及原生 ASan/Valgrind 检漏仍按交付反馈所述未测。
