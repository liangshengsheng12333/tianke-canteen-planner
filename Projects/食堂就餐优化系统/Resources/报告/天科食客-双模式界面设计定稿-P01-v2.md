作者：P01。性质：本轮设计定稿与界面评审基线，供用户看效果和后续 DSH 实施；不表示用户已经满意、代码已经实现或测试通过。

## 1. 简要产品定义

**问题：**当前首页在菜品前连续展示档案、方案状态和诊断，记录及资料页面长期展开多组表单。用户认可能力，但不满意密集程度、文案和视觉。

**目标：**先让用户看清吃什么、去哪买、多少钱、搭配情况和约计热量；完整模式再补具体营养。视觉参考小米官方当前 HyperOS 4 的柔光玻璃、圆润悬浮容器和有序字级，保留天科食客自己的名称与饮食场景。

**成功标准：**用户能够通过新预览明确评价布局、字体、浅深色和双模式，调整后明确认可这一版界面；满意度由用户反馈判断，不能用“页面做完”代替。业务能力在导航调整后均有可达入口，正式流程验证留在最终固定候选上。

**范围：**今日、记录、我的，必要的餐次详情/选菜/确认/资料/设置/菜单备份页面；简易与完整显示；浅色、深色、跟随系统。复用现有业务能力与数据；用户追加确认月历、日期回看和月度汇总纳入本版后续集成。

**约束：**当前先做 UI；不以新核心、真实菜单齐备或全量真机验收作为看设计的前置。演示数据显式标注；实际开发从现有 T05 页面候选起步，保留业务入口，不擅自升级 WASM、改营养推荐或删除旧页面。增肌留下一版本。

**初步方案已收口：**三个主导航、本餐聚焦、相同布局上的信息增减、两组独立设置、雾白/深灰双主题、局部玻璃。待解决的是用户看过新界面后的具体反馈，以及微信中材质和系统主题事件的实际表现；它们不交由执行方自改产品范围。

## 2. 两组独立设置

| 设置 | 选项 | 首次默认 | 影响 |
|---|---|---|---|
| 显示模式 | 简易 / 完整 | 简易 | 营养信息多少，不改变推荐、记录与业务权限 |
| 外观 | 浅色 / 深色 / 跟随系统 | **浅色** | 配色与材质，不改变信息、数据或显示模式 |

用户可自由组合六种状态。设置入口固定为“我的 → 显示与外观”；今日页标题旁的“简易 / 完整”小胶囊也可直接切换显示模式，避免为了看数据反复进设置。

外观规则：

- 浅色固定雾白，即使系统深色也保持浅色；深色固定深灰，即使系统浅色也保持深色。
- 跟随系统按当前系统主题呈现，系统切换、从后台返回时同步；不要求用户重启。无法读到系统主题时暂用浅色，保留“跟随系统”选择。
- 保存的是用户选项，不能把“跟随系统”覆盖为当时解析出的浅色/深色。
- 设置在本地持久化；加载页面先确定外观，减少深色用户看到整屏白闪。具体微信接入方式由实施时核对可用能力。
- 两组设置切换都不触发重新规划、不写记餐、不清空输入、不改变餐次与日期。若设置保存失败，反馈“设置没保存，请重试”；不谎称已持久化。
- 老版本没有此设置时使用浅色 + 简易；不通过新模式批量改写旧业务数据。

## 3. 页面结构

底部主导航：**今日 / 记录 / 我的**。三个入口顺序固定；使用共用导航，不让每页各画一套行为不同的导航。

| 页面 | 首要内容 | 次级入口 |
|---|---|---|
| 今日 | 日期、餐次、本餐菜品/窗口/价格、搭配/热量、换餐与确认 | 自己选菜、本餐详情、其他方案、今日小结 |
| 记录 | 日期、三餐已记/未记、食物与实付、补记 | 编辑、撤销、结束/重开餐次、营养详情 |
| 我的 | 当前目标与简短资料、分组设置列表 | 个人资料、预算与偏好、显示与外观、数据管理 |

“自己选菜”是日常功能，不能藏到开发工具；“完整模式”仍是普通用户界面，不能变成开发者模式。菜单导入、备份、恢复收进数据管理；诊断独立放在数据管理的次级入口，不占主导航。

## 4. 今日页定稿

### 4.1 共用结构

由上至下：微信系统栏/胶囊预留 → 产品标题和日期 → 显示模式快捷入口 → 早餐/午餐/晚餐选择 → 本餐卡 → 今日小结 → 悬浮底部导航。

本餐卡优先展示当前用户选中的餐次。首次进入可根据时间提示餐次，但不能自动结束、确认、补记任何一餐；切换主题或模式也不跳走当前餐次。其他餐次保留清楚的切换入口及已记状态。

卡片信息依次为：

1. “午餐”及窗口；未选择窗口时不捏造。
2. 菜名、份量和计划价格；长菜名正常换行。
3. 热量大数字和一句搭配说明；有估算数据时在这里统一提示。
4. 完整模式增加紧凑营养区，见第 5 节。
5. 主按钮“确认吃了”，次按钮“换一份”；卡片下提供“自己选菜”“这餐详情”。

不放大幅装饰餐图占据首屏；无真实菜图时不生成可能误导为实物的照片。预览中的碗图形只是品牌装饰。

### 4.2 简易模式

正常样例（虚构）：

```text
天科食客                       简易 ›
10月20日 周二

早餐 · 已记        午餐        晚餐

午餐                  二楼 · 家常菜
香煎鸡腿、清炒时蔬、米饭        ¥13
约 600 千卡
主食、蛋白质食物、蔬菜都有
营养为估算值

[ 换一份 ]              [ 确认吃了 ]
自己选菜                     这餐详情 ›

今天已记 1 餐                 查看 ›
```

简易模式主卡不显示三大营养克数/百分比，也不平铺身体指标。用户仍可主动查看详情，不因模式失去选菜、锁定、售罄和预算能力。

### 4.3 完整模式

餐卡布局、主按钮与阅读顺序相同，仅在热量和搭配之后增加：

```text
这餐的营养
蛋白质             30 克          20%
脂肪               20 克          30%
碳水               75 克          50%
[三段细条：热量来源]
```

这组示例满足 4×30 + 9×20 + 4×75 = 600。三个数值行和一条比例条共用一个区块，不再做三张卡或三个大圆环；完整模式允许必要纵向滚动，不通过缩小字体硬塞一屏。

### 4.4 必要的操作归属

- 换一份：沿用约束、同窗优先和现有业务结果；其他方案在详情内按实际策略命名，保留推荐/省钱/口味的取舍说明，不按算法名字包装效果。
- 锁定窗口、锁定菜品、售罄及解除：放本餐详情。已有锁定以简短文字显示在本餐卡；失效锁定直接给原因与“处理锁定”入口。
- 确认吃了：先打开确认区，显示实际吃的菜/份量与实付；可修改或标记未知，再保存。计划价格与实付分别表述；连续点按沿用现有幂等保护。
- 结束餐次与重开：放对应餐次的更多操作；已记餐次进入记录，不能因点击推荐重复记账。
- 今日小结使用“已记录”，不把全天计划当已摄入；预算区把已花、待吃计划和预计全天区分。没设预算不摆空卡，有未知实付则明确“花费还没填全”。

## 5. 营养展示口径已收口

### 5.1 简易模式如何说明搭配

使用已知食物类别说明构成，暂不新增健康分数、红绿健康评级或“绝对均衡”结论。

- 三类均已知：主食、蛋白质食物、蔬菜都有。
- 数据齐全且缺蔬菜：这份没配蔬菜；详情给“自己选菜”入口，不主动修改方案。
- 类别不全：搭配信息待补。不能把未知写成缺失，也不能仅凭菜名猜类别。
- 热量完整但含估算：约 ×× 千卡；已知非估算时显示 ×× 千卡。不额外把整数 kcal 再做十位取整。
- 热量不完整：主卡“热量待补全”，详情显示已知小计和缺项；未知不能显示 0。

### 5.2 完整模式的数值与比例

正式数值取同一份核心餐结果或实际日志汇总。契约能量为整数 kcal，宏量为整数 0.1g；显示克数时除以 10，最多一位小数并去掉无意义的 .0，金额由整数分格式化为元。

比例为本餐三种已知宏量的供能占比。以契约整数单位定义展示计算：

```text
P = 4 × proteinDg
F = 9 × fatDg
C = 4 × carbDg
T = P + F + C
每种比例 = 该种 / T × 100%
```

分母是三种宏量的换算能量总和，**不是**日目标 `composition`，也不是简单的克数之和。主热量继续显示来源中的 `energyKcal`，不为凑比例改写它；详情解释“比例按三种营养的换算热量计算，可能与标注总热量略有差别”。

百分比显示一位小数；采用最大余数分配到总计 100.0%，同余数按蛋白质、脂肪、碳水顺序；比例条也使用此组分配结果，避免表格和条形图不一致。三项全为已知且 T>0 才显示完整比例；有负值/非有限数按无效数据处理。T=0 时显示三项已知 0 克与“暂不显示比例”；任何宏量未知时保留已知值，缺项用“待补全”，不画完整比例条。

这是结果的展示换算，不新增推荐、目标或适用性逻辑，不修改冻结接口。展示逻辑只保留一处供两模式/详情使用；若集成候选无法提供所需数据，保留缺项状态并交 P01 决定，不能让前端编造数据。

### 5.3 面向大众与自动目标边界

本版可提供看菜单、手选和记餐；自动目标沿用冻结契约适用条件。个人目标显示“均衡饮食 / 减脂控重”，手动目标放目标详情内；训练偏好独立。目标不可自动应用时说明原因，保留可用的手选/记录入口。增肌不出现在本版可选目标中。

## 6. 记录、我的与次级页面

**记录：**日期行、可展开的月历、三餐状态、已记食物与实付。默认选今天，点“查看月历”展开日期网格，可切月份并点昨天或任一天，详情见第11节。简易模式只补约计热量摘要，完整模式增加克数，比例在餐详情展示。补记是清楚的独立入口；编辑/撤销归属于具体记录。初次空态“这天还没记餐”并提供“记一餐”；没有记录不显示“摄入 0，今日达标”。历史记录继续读取原快照。

**我的：**不先打开全量表单。顶部显示“我的”和当前目标摘要；下方分为“个人资料”“预算与偏好”“显示与外观”“数据管理”。不增加头像账号、登录、会员或社区占位。

**个人资料：**已存资料先展示，点编辑才进表单；必填/选填与适用性提示继续保留。手动目标仅在选择手动方式时展开，保存与应用状态区分。

**显示与外观：**上半组简易/完整，说明分别为“先看这顿怎么吃”“多看营养数值”；下半组三张浅色/深色/跟随系统小预览。当前选择用边框、勾选和文本共同表达，不能仅靠颜色。

**数据管理：**显示当前菜单和“示例菜单”标识（若为模拟数据），分别进入更新菜单、导出备份、恢复备份。正式确认前展示影响，取消/失败保留原数据。原始 JSON、摘要、诊断放次级页，不让读数据的普通用户面对哈希和内部阶段码。

## 7. 视觉定稿

### 7.1 风格来源与本项目选择

以小米官方当前 HyperOS 4 的柔光玻璃和悬浮框架为视觉参考；使用通透的导航/弹层、圆润容器、大字级和内容分组。官方展示是参考，不把 Android 原生系统材质或其 SDK 当成微信小程序可直接使用的能力。

天科食客采用**雾白 / 深灰 + 低饱和绿色强调**，不因模仿系统统一染成小米品牌橙；背景可有非常淡的绿蓝环境光，菜品区域维持清晰、稳定的底色。状态栏、微信胶囊、安全区与正文各有空间。

### 7.2 主题色令牌

以下是本项目设计值，不是小米官方色值。材料预览可受浏览器/设备影响，正式微信中按同一语义调校。

| 语义 | 浅色 | 深色 |
|---|---|---|
| 页面底 | #F5F6F8 | #111416 |
| 主卡片 | #FFFFFF | #202629 |
| 次级容器 | #ECEFF0 | #2A3235 |
| 主要文字 | #202825 | #F1F5F2 |
| 次级文字 | #65716B | #AFBAB4 |
| 强调文字 | #267354 | #90D6AD |
| 主要按钮底/字 | #267354 / #FFFFFF | #90D6AD / #13271D |
| 温和提示底/字 | #FFF3DB / #80550B | #3B3020 / #F0CC8B |
| 错误文字 | #B6373F | #FFB4B9 |
| 玻璃底 | 白色约 76–88% | 深灰约 80–90% |

深色单独调整边缘高光、分隔线、阴影、图标和弹层遮罩，避免整屏纯黑或对浅色做机械反色。菜品照片保持正常内容；缺图不用大面积白框。

### 7.3 字级与空间

以 375px 设计宽度为基准；微信实现可按 750rpx 设计坐标转换，不能把示意数值当真机已验证。

| 角色 | 字号/字重 | 行高 |
|---|---|---|
| 产品/页面标题 | 28px / 650（不可用则 600） | 1.25 |
| 本餐热量数字 | 38px / 600 | 1.15 |
| 菜名/价格 | 18px / 550（不可用则 500） | 1.45 |
| 正文/按钮 | 16px / 400–600 | 1.5 |
| 日期/来源/标签 | 13–14px / 400–500 | 1.5 |

优先系统无衬线字体，设备已有 MiSans 可使用；不为这一版先下载全量字库。字体区分来自字号、字重、字色和留白，正文不混搭多个装饰字体。

页面左右 20px，主要卡片内边距 20px、圆角 28px；组间距约 20–24px，组内 8–12px。按钮高度 48px，交互区域至少 44×44px。价格/关键提示允许换行；大字设置下先让页面变长，避免截掉必要信息。

玻璃重点用于底部悬浮导航、模式胶囊和弹层，内容卡保持较实。导航选中态有明确文字/图标反馈；次级页有返回入口。使用一个共用导航组件，真实材质不支持时改用相同布局的高不透明度底与轻边缘光，不牺牲字的清晰度。

动效只做轻按反馈、模式内容切换和弹层过渡，参考约 160–220ms；尊重减少动态效果设置。不开持续粒子、流光背景或无意义呼吸动画。动效数值是设计初值，不是响应性能验收线。

## 8. 文案与状态

| 场景 | 展示与动作 |
|---|---|
| 未建资料 | 想按你的目标推荐？先完善资料。/ 完善资料；手选和记餐入口仍可用 |
| 示例菜单 | 日期下方简短“示例菜单”，查看说明可知不是真实供应；不每卡重复长警示 |
| 已有合法近似方案 | 已找到可用搭配，计算尚未完成。/ 查看说明；不得宣称最优 |
| 限额且没找到 | 这次还没找到合适搭配。/ 调整条件；不写“证明无解” |
| 约束下确无候选 | 当前条件下没有可选菜品。/ 检查锁定或售罄 |
| 超预算 | 预计比剩余预算多 ¥×。/ 换一份；不藏到信息总数徽标里 |
| 价格不全 | 花费还没填全，暂时算不准预算。/ 去补充 |
| 目标不可自动应用 | 暂时不能按这个目标推荐。/ 查看原因；同时给可用的自己选菜入口 |
| 保存失败 | 没保存成功，原记录还在。/ 重试 |
| 已记餐次 | 已记录。/ 查看记录；不得把同一份重复确认 |

只有成功的短反馈可用轻提示；需要用户处理的原因与操作保留在页面。简易和完整使用相同直白表达，不向完整模式用户堆状态码。错误、未知、锁定失效在两种主题都清楚可读。

## 11. 本版后续集成：月历与饮食回看

用户先提出留下一版本，随后明确改为本版后续一起集成：按月查看饮食数据，点某一天回看昨天或其他日期吃了什么。以后一条决定为准；现有日期记录/回看基础不等于月历或月度汇总已经实现。

记录页默认显示今天，标题下提供“查看月历”；展开后按周一到周日排列，支持前后月份、当天标记、已选日期和有记录标记。点日期刷新下方当天三餐详情，保留月历与选中状态，提供“回到今天”；切换月份时选新月份最近的合法日期，不跨月误用旧日。

当天展示各餐食物、份量、实付和已有营养；历史信息从原记录快照读取，不用当前菜单覆盖历史菜名/价/营养。修改、撤销、补记沿用现有业务，成功后日/月汇总同步更新；被撤销或被替换的版本不重复计入。

月度汇总采用短卡：“本月已记 X 天 · Y 餐”，已知花费与已知热量各一行，有未知则标“含未填项”；详细宏量仅在完整模式/详情显示。没有记录不能等同没吃，未记餐不能按零摄入计算，不对整个自然月的缺记录日期制造零摄入。当前不增加自动健康评分、月度达标率或复杂统计图。

本版已有的按日期记录/查看基础保留；新增重点是月历浏览和月度汇总，不重复造独立记录库。当前先在独立界面预览中演示，实际日志接合放在界面确认后的实施阶段。新增功能列入本版相应集成与集中测试范围；增肌仍维持下一版本待办。

用户对当前展示的界面预览反馈“做的太漂亮了”，记录为视觉方向的正面反馈，不扩大为正式小程序、所有页面或业务验收通过。
