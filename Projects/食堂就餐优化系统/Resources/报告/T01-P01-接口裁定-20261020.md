## P01 已裁定内容

1. **数据结构与数值**：以 DSH 当前提案正文 v1.1 的版本化结构及 `ResultEnvelope` 为主。金额整数分、能量整数 kcal、宏量营养用整数 0.1g（`proteinDg`/`fatDg`/`carbDg`，显示时转 g）；未知用 `null`，已知零用 `0`；体重 g、身高 mm。旧页面数值/枚举只记对应关系，不做旧格式兼容层。
2. **算法、策略与营养归属**：统一算法 `greedy`/`dp`/`branchAndBound`，策略 `primary`/`economy`/`taste`；Profile 目标 `maintain`/`fatLoss`/`manual`，另设 `trainingPreference`。首版不含反重力提案中的 `muscle_gain`。正式营养公式、目标和预算汇总由 C++ 核心唯一计算；Profile 只存输入和手动专业目标。派生值可缓存，但须带输入 `revision`/`configVersion`，不能在页面独立复算。
3. **请求与当日状态**：`PlanRequest` 使用 `planningMeals[]` 支持 1–3 个待规划餐次，传入当前 Profile、Catalog、Config 和当日有效 `MealLog` 快照；不只传 `menuVersion` 或页面汇总的 `todaySpent`。目标和预算由核心重算。默认策略 `remainingAfterKnownIntake`；摄入不完整时按 PRD 3.1 回到餐次参考并标不完整，不追加补偿。已吃或用户结束的餐次不可被规划；补记可保留。
4. **错误与结果**：按 DSH 信封分层；无解、数据不足、锁定失效、资源受限分别可见。营养/价格完整性与近似状态分别标记；`OkPartial` 不等于营养全缺失或已通过。
5. **菜单与套餐**：营养主数据和售卖 `offer` 分离，保留固定套餐 offer 与可选套餐规则。可选套餐荤素数量、候选组件、含饭与总价在菜单中显式表达，由 C++ 共用候选生成层展开，页面不另写组合或营养计算。固定套餐优先采用独立营养；否则仅在组件、份量和营养来源明确时由核心汇总并标估算/不完整，不补造未知。套餐只用真实总价，不按组件价拆价或重复计入含饭。DSH 按此补一个最小确定的 `comboRules` 结构和示例，不扩为通用规则引擎。
6. **半份米饭**：只有米饭允许半份；半份营养按半份计算，价格与同窗口、同米饭的整份相同。半份 offer 显式记录整份真实售价，不除以二，也不要求另行提供半份售价；整份价格未知时半份仍未知。自动预算方案只有价格完整时才可标记预算内；手选/历史未知价保留已知小计并标记不完整。套餐按真实总价，含饭不额外收费。
7. **记餐与结束餐次**：确认幂等由反重力存储层实现；`MealLog` 带 `confirmationId` 与稳定 `recordId`，改撤保留快照关联。核心只消费当前有效日志并防重复 ID 入账。用户结束餐次单独记录在 `state.endedMeals`，不伪造 `SKIPPED` 摄入或零消费。
8. **WASM 导出**：采用 DSH 的 `mp_plan`/`mp_nutrition_target`/`mp_validate_menu`/`mp_alloc`/`mp_free`/`mp_api_version`/`mp_contract_version`。原生与导出复用同一核心。JS 输入和输出缓冲区在 `finally` 各释放一次；输出先复制后释放，版本字符串静态且不释放。核心异常转成边界可见错误，空指针只代表真实分配失败。单实例串行，不加并发框架。
9. **性能与一致性**：耗时不放入语义一致性比较的规划结果；原生/WASM 算法耗时及页面端到端耗时独立测量。状态/节点数可语义回显。一致性使用确定性限额和 `wallClockMs=null`，不承诺不同机器限时产生相同字节结果。
10. **策略排序**：`primary` 先按营养偏差排序；`economy`/`taste` 先按同一 `nutritionTier`，再分别优先价格/口味。工程初值 `nutritionTier=floor(nutritionDeviationBp/1000)`；1000bp 是可调排序分组宽度，不是营养达标阈值或医学指标。四项营养偏差权重各 250‰，三算法使用同键。完整方案可计算 tier；不完整方案只作参考，不比较为已达标。固定未知项相同的候选可按已知可比部分比较，并标明 basis 不完整。保留不足三套的说明，不复制凑数。
11. **次级多样性排序**：首版采用简单类别覆盖/重复菜惩罚，排在各策略主要键之后、`planKey` 之前；不增加模型或复杂优化。未知类别不计覆盖，菜单字段需明确。三策略均用稳定 `planKey` 最终打破并列。
12. **目录和归属**：本轮唯一契约候选位于 `Resources/契约/T01-v1-candidate/`，由 DSH 独占写、P01 决策控制。后续 `core/{include,src,cli,wasm,tests}/` 和 `tools/core/` 归 DSH；`miniprogram/` 和 `tools/miniprogram/` 归反重力，双方不交叉写入。`Resources/菜单/` 归反重力；`Resources/营养配置/` 由 DSH 起草、P09 核验；报告各自独立命名，共享契约变化交 P01。
13. **本轮候选规模**：只需唯一 `contract-v1-candidate.md`、`nutrition-v1-candidate.json`（标清已确认产品初值/待独立核验）和一个配对 JSON 样例。契约文件内含模块归属、两层独立参照、性能测量与注释率口径；性能数字由 T02/T07 实测，不写成已达成的 300ms。文件候选生成后记录版本和必要哈希，不加多层内容寻址或兼容框架。
14. **营养核验与冻结门槛**：营养参数、范围和算例待 P09 独立核验，可指出需改值，但不得把示例当已核验建议。P09 核验与 DSH 修订并行；DSH 修订、反重力对齐、P09 核验结果齐备后，由 P01 判断冻结。任何人不得据此自动启动 T02/T04/T05。
