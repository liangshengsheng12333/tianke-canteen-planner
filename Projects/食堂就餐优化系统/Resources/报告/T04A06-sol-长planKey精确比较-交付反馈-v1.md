## 3. 从实际约束导出的紧上界

以固定快照为定位依据：

1. `contract.cpp:105–123`：稳定 ID 仅含 ASCII 小写字母、数字、点、下划线、连字符，长度 1..64。因此窗口 ID、静态 offerId、ruleId、dishId 均不需要 JSON 转义，也不会出现 UTF-8 多字节膨胀。
2. `catalog.cpp:343–376`：requiredCounts 每类 1..6，总组件数 1..8；展开为不放回组合。`catalog.cpp:491–503`：展开 ID 为 `ruleId#dishId+...+dishId`，组件按字节序升序。若组件数为 c，则长度上界为 `64 + 1 + 64c + (c−1) = 64 + 65c ≤ 584`。
3. `planner.cpp:34,3080–3081`：每餐购买项总数最多 8，包括锁定数量。套餐组件数不计为购买项。组件互斥只要求同餐所购套餐不共享底层单品；目录没有将全餐组件数再限制为 8。
4. 正式 `BuildPlanKey`（1095–1188）按早餐、午餐、晚餐顺序输出 `[[meal,windowId,[[offerId,quantity],...]],...]`；同餐同 offerId 合并数量，offerId 升序。数量 1..8，只有一个十进制数字；合并减少元组数，不增大界。DP 的 16 对项目临时数组本身足够，因为每餐不同报价最多 8 对。

设实际存在 M 个餐次、每餐有 p_m 个合并后的报价对，其 ID 长度为 L_mi；餐次名与窗口 ID 字节长度分别为 a_m、w_m。紧凑 JSON 的精确长度为：

`N = 1 + Σ_m [ a_m + w_m + 10 + Σ_i (L_mi + 7) ]`。

其中每对 `["offerId",q]` 占 `L+6`，相邻对逗号再计 1；外层及餐次分隔的剩余常数合并为上述式子。最大三餐的餐名长度之和为 `9+5+6=20`，窗口 ID 总长最多 192，报价对最多 24 个，故：

`N ≤ 1 + 20 + 192 + 3×10 + 24×(584+7) = 14427`。

**可达性证据**：`*-tight-bound.request.json` 使用 64 个不同、长度 64 的单品，分成 8 个不重叠的 8 组件组；每组为 protein 6 + vegetable 2。8 条长度 64 的规则、一个长度 64 的窗口，全部供应三餐，每餐锁定这 8 个套餐各 1 份。目录与请求均通过核心校验，组件互不重叠、无含饭互斥；每餐只有一个候选。正式输出键与独立生成的 14427 字节规范元组 SHA256 一致。输入 planningMeals 故意倒序，正式键仍按早午晚顺序生成。

作为参照：若全部为长度 ≤64 的静态 offerId，界为 `243+24×71=1947`，所以 A01 的静态短键结论不需要推翻。若全天购买项目总数 ≤6，则不同报价对也 ≤6，即便给足三餐头部，界仍为 `243+6×591=3789<4096`；因此溢出至少需要 7 个购买项。

## 4. 有效最小溢出反例与错误结果

### 4.1 输入与合法性

最小复现入口：`baseline-4097-minimal.request.json`。只规划午餐；一个 ID 为 `w` 的窗口；无预算、无已吃记录、无口味词。沿用冻结营养配置和既有合法档案，日目标为 `(2370,840,711,3485)`。

56 个长度 64 的单品分为 7 个互不重叠的组，每组 8 个。每组 protein 6、vegetable 2；所有营养已知，来源标注为合成估算。前 6 组各有一条长度 64 的规则，锁定其展开报价各 1 份；第 7 组有 `z000000` 和 `z000001` 两条等营养、等价 100 分的规则，二者使用同一第 7 组组件，因此互斥。每组 candidateDishIds 以逆序提供，实际展开 ID 由核心统一排序。没有独立报价的组件按规则随套餐供应，符合现有目录语义。

最终只有三个候选：

| 候选 | 规范串字节数 | 偏差 bp / tier | 价格分 | 说明 |
|---|---:|---:|---:|---|
| 6 项锁定基底 | 3563 | 1405 / 1 | 600 | 不能胜过 tier=0 的两种完整组合 |
| 基底 + z000000 展开报价 | 4097 | 0 / 0 | 700 | 应胜出 |
| 基底 + z000001 展开报价 | 4097 | 0 / 0 | 700 | DP 实际错误胜出 |

两种 7 项组合都有营养完整、覆盖类别 2、重复对数 0、未知分类 0、口味 0、价格完整，所有先于 planKey 的比较字段完全相同。其规范串长度恰好为：

`1 + (5+1+10) + 6×(584+7) + (527+7) = 4097`。

7 项同餐之间没有组件重叠；两个替代套餐从不同时购买。该例没有利用锁定冲突、非法字符、过长稳定 ID、不合法 requiredCounts 或营养缺失制造失败。

### 4.2 完整哈希与截断哈希顺序相反

| 第 7 项规则 | 正式完整 4097 字节 SHA256 | 实现实际取前 4096 字节 SHA256 |
|---|---|---|
| z000000 | `6c2a0a4ee5904585b0f972ec608fb2a89b172a6baa2d6aa229d48cb74c6fd2cd` | `246d1c0a08a0038e627f390e71428d1337cbcd06a93c4273893ed59360e12883` |
| z000001 | `ddccd42119e11d9fbb641d7ce58da95ff3f0fbf19ca6b4203b3e81defd8ee8c3` | `07abfae8f9a5c39e696455fa3db2615e097a302be166ab459e1e5b61bdf80310` |

正式键应选 `plan:6c2a...`；截断键却选 `07ab...` 对应的 z000001。此例丢掉的仅是 JSON 最后一个 `]`，仍足以改变 SHA 排序。完整规范串原字节见 `baseline-4097-tied-0/1.canonical.json`。

根因：`StackJsonBuf::PutChar` 在第 4097 字节时只设置 overflow，size 停在 4096；`ComputeTerminalDpPlanKeyHex`（1975–2062）无视 overflow，仍调用 `Sha256(buf.data,buf.size,...)`。终端支配（2144）据此删掉真正更小的正式 planKey。后续 `BuildPlanKey` 对剩余方案正确计算完整摘要，所以**响应中的单个 planKey 本身是正确的，但被选中的方案错误**。

最小例实际返回 `OkPartial`，表示只规划午餐；其 score 的营养完整性仍为 complete，不能把该业务状态误读为输入失败或营养缺失。三策略均指向错误的 `plan:ddccd...`，同时报告完整搜索、3 状态、无限额与近似项。

完整未锁定版本有 191 个合法单餐子集，独立穷举和 CLI 均核对候选数；其 DP 同样错误，BnB 辅助对照选中正确的 `plan:6c2a...`。真值依据是独立枚举和完整 SHA，而非 DP/BnB 相互一致。

## 5. 最小可实施修正与等价性证明

仅供 P01 安排核心唯一写入者移植：`proposal.patch`，固定基线为本报告的 `417E...`；不能用隔离整文件覆盖同时进行的其他核心改动。

提案只改一个隔离 planner.cpp：

1. 从正式 `BuildPlanKey` 提取单一私有 `WritePlanKeyRows`，保留早午晚顺序、同 ID 数量合并、offerId 字节排序以及 JsonOut 字符串/整数语义。正式输出仍由它生成元组，再用既有 Sha256 取摘要和 `plan:` 前缀。
2. 每个 DP 终端候选在支配去重前，用相同 helper 对已经确定的完整餐次选择计算一次 SHA256，将既有 `Sha256Digest`（32 字节）存入状态。非终端不使用此字段，也不新增前缀哈希剪枝。
3. 终端全指标平局时比较摘要原始无符号字节，删除 StackJsonBuf 与专用手写 JSON 转义/排序/哈希路径。
4. `keyMeals`、`keyPairs`、`keyJson` 在一次 RunDpAlgorithm 中初始化一次，Clear/重置长度后复用容量。不会每个候选新建、释放 Arena；WASM 当前 bump 分配器只有所有存活块归零才复位，按候选创建 Arena 会在单请求内不断推进堆。此提案不用修改分配器，也不扩大固定 JSON 数组。

**等价性**：终端状态 choice 数组指向与正式 EvaluateFullDayPlan 相同的完整 MealPlan 集合。两条路径调用同一个 helper，故按早午晚选择的餐次、窗口、合并数量、排序后 offerId 以及每个 JSON 字节都相同；因此完整摘要相同。所有正式键有共同前缀 `plan:`，其后的 64 字符为同长小写十六进制。第一个不同的摘要字节的大小，与它展开的两个 hex 字符的字典序相同；`MemCompare` 使用 unsigned char，故比较 32 字节摘要与比较完整正式 planKey 等价。摘要完全相同也与正式键相等语义一致。

缓存写入发生在终端支配之前，非终端不会读取；缓冲引用仍指向请求内有效的不可变候选，没有引入新输入校验层或多个兜底算法。长度超出 4096 只是动态 TextBuffer 的正常增长；真实分配/序列化失败沿一条失败出口上报，不以截断摘要伪装成功。

复杂度：每个终端候选做一次完整序列化与 SHA，后续终端平局比较为最多 32 字节。JSON 工作缓冲按见过的最大串增长、容量复用，当前紧上界对应 TextBuffer 容量 16384；每个 DP 状态增加 32 字节摘要。提前为每个终端候选求摘要会增加不发生平局时的工作量，其在全规模/WASM/红米上的性能尚未测量；本卡不据小例声称性能已达标。
