## 4. 紧邻交互检查与真实前端缺陷定位 (Defect Audit)

在真机交互测试环节，用户在真机上进行了菜单切换与锁定处理操作，取得了重要的系统完整性验证成果，并**精准捕获、定位了一项严重的前端逻辑缺陷**：

### 4.1 数据完整性安全门禁机制验证（通过）
- **测试动作**：用户在数据管理中将菜单切换为西院西一食堂真实菜单（T03d）；
- **实测现象**：由于本地历史数据中存在模拟菜单下的旧米饭锁定（`offer-rice-full` 与 `offer-rice-half`），系统在刷新方案时准确识别出“旧菜品报价已不在当前菜单中”，严格拦截了非法方案生成，并弹窗提示：`锁定失效/冲突，需先处理`（见证据 `06-菜单切换锁定冲突与完整性校验.jpg`）；
- **结论**：验证了“输入改变后旧冲突不产生脏数据、不静默放行”的契约安全要求。

### 4.2 捕获前端代码严重缺陷：锁定解除死锁（DEFECT-T08A1-01）
- **缺陷现象**：在首页“锁定项需要处理”卡片中，用户点击黄色按钮 **“解除菜品锁定”** 时，系统未解除锁定，反而弹出 Toast 报错：**`该报价已不在菜单中，无法锁定`**，导致用户在当前 UI 上陷入死锁，无法通过点击解除失效锁定（见证据 `07-锁定解除死锁Toast证据.jpg`）。
- **根因代码溯源**：
  - 源码位置：`miniprogram/src/pages/home/index.ts` 第 263–273 行：
    ```typescript
    const lockIssues = view.lockIssues.map((issue, index) => ({
      index,
      kind: issue.kind,
      kindLabel: issue.kind === 'window' ? '窗口锁定' : '菜品锁定',
      mealLabel: MEAL_LABELS[issue.meal],
      label: issue.label,
      reason: issue.reason,
      windowId: issue.windowId || '',
      offerId: issue.offerId || '',
      resolvable: issue.kind === 'window' ? !!issue.windowId : !!issue.offerId,
    }));
    ```
  - **缺陷原因**：该映射漏传了 `meal: issue.meal` 属性，导致 WXML 中 `data-meal="{{item.meal}}"` 传递为空（`undefined`）；
  - 当触发 `onClearItemLockIssue` 调用 `store.toggleItemLock(undefined, offerId)` 时，`day.itemLocks.findIndex` 无法用 `undefined` 匹配已有锁定，进而错误穿透至“添加锁定”分支；又因当前菜单中已无该旧 offerId，导致返回 `该报价已不在菜单中，无法锁定` 报错。
- **影响评估**：属于生产 UI 层的阻断性交互 Bug（不影响底层 WASM 与核心算法）。在当前候选未修复前，真机可通过“诊断页 $\to$ 清除本机数据”复位状态来绕过。

### 4.3 捕获前端交互缺陷：换一份自动强锁定导致不可二次换菜死锁（DEFECT-T08A1-02）
- **缺陷现象**：用户在首页点击“换一份”选择替代菜品后，系统自动将新换入的菜品变为“已锁定”状态。当该餐次只有 1 道菜时（如早餐只有 1 份“山东杂粮煎饼”），再次点击“换一份”按钮，系统直接拦截并弹出 Toast 报错：**`没有可替换的菜品(锁定项不能直接换)`**，导致用户无法在首页继续换菜（见证据 `08-换一份自动锁定与热量待补全证据.jpg`）。
- **根因代码溯源**：
  - 源码位置：`miniprogram/src/domain/store.ts` 第 761 行与 `pages/home/index.ts` 第 735–738 行：
    ```typescript
    // store.ts 第 761 行：换菜直接强行写入 itemLocks
    nextDay.itemLocks = others.concat(desiredOfferIds.map((offerId) => ({ meal, offerId, quantity: 1 })));

    // home/index.ts 第 735 行：换菜前过滤掉所有锁定项
    const replaceable = mealView.items.filter((item) => !item.locked);
    if (replaceable.length === 0) {
      wx.showToast({ title: '没有可替换的菜品（锁定项不能直接换）', icon: 'none' });
      return;
    }
    ```
  - **缺陷原因**：`swapOffer` 强制将换入的菜品打上 `itemLocks`，而单品餐次在锁定后未锁定菜品数归零（`replaceable.length === 0`），导致再次点击“换一份”被代码死锁，必须跳转至次级详情页手动解锁才能继续换，交互设计违背直觉。

### 4.4 真实菜单营养数据核验：31/35 道菜待补全表现与契约严格一致（OBSERVATION-T08A1-01）
- **实测现象**：换至“山东杂粮煎饼”后，页面清晰展示“热量待补全”、“这份没配蔬菜”、“这餐的营养：蛋白质/脂肪/碳水 待补全”、“锁定项营养未知”，且不提供宏量三大营养素热量占比条（见证据 `08-换一份自动锁定与热量待补全证据.jpg`）。
- **契约对照**：依据 T03d 正式成包与 T08 验收契约，当前西院西一食堂 5 窗 35 道菜中，仅原味肠粉、瘦肉肠粉、白切鸡饭、手抓饼 4 道具备依据估算，其余 31 道菜营养均为未知。真机实测客观印证了“未知营养不按 0 计算、不虚饰完整、规范呈现待补全”的契约表现。

### 4.5 9 场景算法覆盖边界说明（受限项）
- **提示词要求**：测量 G1/G2/G3 × greedy/dp/branchAndBound 共 9 个场景。
- **现场实测受限原因**：当前被固定的生产前端候选在 `domain/app-state.ts`、`domain/plan.ts` 与 `utils/capability.ts` 中硬编码了能力门禁 `algorithm === 'greedy'`，真机 UI 无法直接切换执行 `dp` 与 `branchAndBound`。
- **口径处理**：严格遵守提示词第 28 行与“代码只读”约束，不篡改生产代码造假；真机仅实测 Greedy 真实端到端指标，dp/bnb 标记为**真机前端未开放/受限**，算法核心指标引用已在 T07b 宿主上严格验证的稳定基准（G1–G3 dp/bnb 核心耗时 12.8–69.4 ms）作为对照。
