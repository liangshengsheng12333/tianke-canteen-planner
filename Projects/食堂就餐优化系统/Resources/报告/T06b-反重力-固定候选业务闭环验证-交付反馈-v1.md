## 三、五组业务闭环情境逐项验证结果

反重力在隔离测试环境（内存隔离存储 + 注入业务时钟 + 真实包内 A11 WASM + 真实 T03d 菜单）下执行综合业务闭环验证，五组情境逐项结果如下：

### 情境 1：推荐与自选 —— 【PASS】
- **预期行为**：用当前真实菜单创建隔离档案，走一次推荐和一次手动选择；确认窗口、餐次、套餐/份量、营养未知状态与选择一致。未知营养可手选并保持未知，不能按零显示或声称满足目标。
- **实际观察与验证操作**：
  1. 保存隔离档案（20岁男/175cm/70kg/日预算25元），`computeTarget()` 成功生成目标（状态 `Ok`，目标热量 2370 kcal）；
  2. `refreshPlan()` 规划成功（状态 `OkPartial`，生成有效 planKey，预算内 `overBudget: false`）；三餐推荐中包含的未知营养菜品，在视图中均严谨标为 `null/未知`，绝未虚假显示为 0 kcal；
  3. 午餐调用 `getSelfPickView('lunch')` 查看真实窗口与菜品；选中武汉热干面窗口的未知营养菜品（`estimated: false`，价格 8.00 元）；
  4. 草稿预览 `previewSelfPickDraft` 成功，价格完整显示 8.00 元，`nutritionSums` 严格保持 `null`（不补 0）；
  5. 确认自选餐 `confirmSelfPickMeal` 成功落账，生成真实记录 ID，午餐状态转为已确认，首页提示 `planNeedsUpdate: true`，未污染用户数据。
- **原始证据**：`01-推荐与自选/01-target-outcome.json` 至 `07-home-view-after-self-pick.json`。

### 情境 2：确认与记录编辑 —— 【PASS】
- **预期行为**：确认一餐后重复确认，不重复记账；修改、撤销、补记后核对有效记录、实际支出及汇总同步更新，已确认快照和已吃记录不被重算覆盖，重算只影响未吃餐。
- **实际观察与验证操作**：
  1. 首次确认早餐生成 1 条活跃记录（已确认餐数 1）；再次点击确认早餐，系统准确拦截并返回 `duplicate: true`，活跃日志数保持 1，支出金额未翻倍；
  2. 调用 `editLog` 修改早餐记录，系统安全创建新 active 记录，并将原记录标记为 `superseded` 存入历史，有效记录与总支出同步更新；
  3. 调用 `revokeLog` 撤销该记录，active 记录清空，原记录标记为 `revoked` 转入历史，已确认餐数与实际消费同步回退；
  4. 调用 `addManualLog` 手动补记早餐（原味肠粉/6.00元/未知营养），补记成功落账，支出更新为 6.00 元，未知营养保持 null；
  5. 重新调用 `refreshPlan()`，系统识别早餐已吃，规划严格只对未吃餐（午、晚）生成新推荐，早餐已吃快照不受覆盖。
- **原始证据**：`02-确认与记录编辑/01-confirm-breakfast.json` 至 `06-replan-only-uneaten-meals.json`。

### 情境 3：余餐预算 —— 【PASS】
- **预期行为**：覆盖已知支出下可行与预算不足/已超预算情形；核对余额计算、未知实付时“不完整”的提示，以及主方案不暗超预算。价格未知或无合法余餐时不得伪称预算内可行。
- **实际观察与验证操作**：
  1. 日预算 25.00 元，早餐确认实付 5.50 元（手抓饼），系统准确核算剩余可用预算为 19.50 元（`remainingKnownCents: 1950`），状态标记为已知完整；
  2. 模拟补记一餐价格未知（`priceKnown: false`），系统严谨标记 `spentPriceIncomplete: true`、`accountingComplete: false`，文案显示“实付待补全”，绝不按 0 元假定；
  3. 设置极低日预算 1.00 元（100分），在真实菜单无任何方案 <= 1.00 元的情形下，`refreshPlan()` 明确返回 `overBudget: true`，主方案显式标注超预算，绝无暗超预算行为。
- **原始证据**：`03-余餐预算/01-normal-budget-feasible.json` 至 `03-over-budget-flagged.json`。

### 情境 4：跨日、售罄与锁定 —— 【PASS】
- **预期行为**：用现有测试时钟模拟跨日，不改主机系统时钟；确认新日不继承前日锁定/售罄且历史日期不被改写。标记已锁菜售罄后验证已吃快照保留、失效锁定有提示并要求用户处理，解除售罄后按新状态更新未吃餐。
- **实际观察与验证操作**：
  1. 在 Day 1（2026-10-23）标记午餐售罄、锁定晚餐菜品并确认早餐；
  2. 注入时钟推进至 Day 2（2026-10-24），系统进入新业务日期：Day 2 售罄列表为空、锁定列表为空（未继承前日状态），已确认餐数重置为 0；Day 1 的历史日志与售罄状态在持久化存储中完好保留；
  3. 在同一天锁定菜品后标记其售罄，触发 `refreshPlan()`，系统在调用核心前安全拦截并返回 `LockConflict`，明确提示锁定项已售罄，锁定标记未发生静默解锁；
  4. 调用 `clearSoldOut` 解除售罄后再次规划，方案顺利恢复（`OkPartial`），锁定菜品正常入选。
- **原始证据**：`04-跨日售罄与锁定/01-day1-soldout-and-locks.json` 至 `05-clear-soldout-restores-plan.json`。

### 情境 5：菜单导入与备份恢复 —— 【PASS】
- **预期行为**：分别验证导入预检后取消、导入失败均保留原菜单和计划；成功导入前确认影响提示，成功后旧计划失效并关联新菜单版本。导出后在隔离状态恢复，再逐项对比档案、菜单、记录和关键快照；仅文件存在不算恢复成功。
- **实际观察与验证操作**：
  1. 传入损坏 JSON 调用 `preflightMenu`，系统在 `parse` 阶段安全拦截，原菜单版本与计划保持不变；
  2. 传入合法新菜单预检成功签发 token，但放弃确认，当前菜单与计划完好保留；
  3. 确认应用新菜单后，菜单版本成功更新为新版本，原计划安全失效置 `null`，首页计划状态重置为 `idle`；
  4. 调用 `exportBackup()` 导出完整备份数据，包含 profile、catalog、days、settings 与完整 SHA-256 摘要；
  5. 篡改当前内存与存储数据后调用 `preflightRestore()`，产出规范的 8 行结构化对比表；调用 `applyRestore()` 完成恢复，逐项严格核对档案年龄（20岁）、日预算（25元）、菜单版本（`west1-canteen-batch1-nutrition4-20261023`）、已确认餐数（2餐），恢复后状态与备份前完全一致，8 行对比全等。
- **原始证据**：`05-菜单导入与备份恢复/01-preflight-corrupted-json-rejected.json` 至 `06-backup-apply-restore-verified.json`。
