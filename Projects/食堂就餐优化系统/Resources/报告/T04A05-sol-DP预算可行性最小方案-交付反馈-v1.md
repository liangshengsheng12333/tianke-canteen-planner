## 1. 建议结论

**可用一个直接改动修补 F6 的预算存在性损失：DP 发生状态截断后，从已经生成的各餐合法候选池中，各取价格完整且总价最低的候选；组合成一份预算可行见证，作为额外终端候选参与现有三策略比较。** 不让它再经过桶化，不占 `maxDpStates` 槽位，不强制它取代更好的预算内 DP 结果，不重跑搜索。

适用条件是：设置了预算；已吃价格完整；已知已吃支出没有超过全天预算；各餐候选池已正常生成，构造及终端评估正常完成。满足这些条件时：

> **若已生成候选池中存在价格完整、满足本日预算的合法全天组合，则加入这一份见证后，每个请求策略都能返回预算内方案。**

这是**候选池内的预算可行性保证**，不是原菜单全部组合的存在性保证、营养达标保证或三策略全局最优保证。`searchComplete` 和原有截断标记不能因此清除。F5 的笼统全局营养误差上界仍应撤回；本方案不重做 DP，也不声称修复 F5。

当前架构下，不需要再增加“营养完整/不完整两套最低价通道”：自动新增候选必须四项营养完整，未知营养只能来自每餐固定锁定项或固定已吃记录，因此同一请求内所有可选组合的营养完整性相同。完整性优先次序不会使上述最小方案失效。

本卡同时复现了一个必须明说的既有预算边缘：**预算 100、已知已花 101、余餐价格 0，固定 A03 核心仍返回 `overBudget=false`。** 原因是先把负余额夹为 0。本方案不在“已经花超预算”的情形作预算内承诺；该既有语义缺口列在第 6 节，未自动扩大修复范围。

## 3. 最小算法及实施位置

### 3.1 一次线性扫描，一份终端见证

记第 m 餐已生成合法候选池为 `C_m`。直接读取每个候选已经汇总的 `priceComplete`、`knownPriceCents`，扫描一次取价格完整的最低价候选。相同价格保留现有候选顺序中第一项即可；**这个局部平局规则只选一个见证，不宣称选中了全部同价组合中的最优 planKey。**

建议只在 DP 已触发 `maxDpStates` 且预算适用时做，保持未截断路径不变。伪代码如下，表达算法位置而非已实施补丁：

```text
正常完成 DP 阶段，保留原有 tracker 与限额标记
初始化现有 bestForStrategy / hasBestForStrategy

if dpCapTriggered and hasBudget and intake.priceComplete
   and intake.knownPriceCents <= budgetCents:
    selected[0..M-1] = 每餐价格完整、knownPriceCents 最低的候选索引
    # 若任一餐没有价格完整候选，就不构造预算内见证
    if 每餐均选到 and sum(selected.knownPriceCents)
                         <= budgetCents - intake.knownPriceCents:
        witness.meals = 所选已有 MealPlan
        用现有 EvaluateFullDayPlan 评估 witness 一次
        把 witness 按现有终端候选处理逻辑放入各策略比较

继续原有 currentLayer 终端遍历、策略比较与输出
```

固定参考最小修改点：`RunDpAlgorithm` 的终端 `bestForStrategy` 初始化之后、原终端循环之前（2334–2339）。复用现有 `EvaluateFullDayPlan` 和终端策略处理（2350–2367），不新增比较器、营养/价格计算或结果格式。预算、锁定、供应等输入已经在入口/候选生成阶段处理，不在新块中重复校验。

正常资源且各餐池非空、`maxDpStates≥1` 时，每阶段至少保留一个状态：笛卡尔积非空，支配不可能删除最后一个状态，桶化后也至少一桶，截断至少保留一个。因此不必为了此方案另建“空层恢复”或资源失败重试通道。若真实分配/构造/评估失败，仍按原错误路径处理，本方案不承诺资源耗尽时仍交出见证。

### 3.2 成本和限额口径

- 选索引耗时 `O(Σ_m |C_m|)`，额外索引空间 `O(M)`，当前 M≤3；另增加一次普通终端方案评估及至多 3 次策略比较。
- 这份完整组合不进入中间状态层，不把 K 个 DP 状态变成 K+1，不改变桶键/桶代表，也不为每桶保留第二份状态。
- `statesEvaluated` 继续采用原有 DP 转移计数口径；原终端评分本就不按额外转移计数，新见证同样不是 DP 阶段转移。后续实施需在说明中记录新增的一次终端评估，不能伪称没有额外工作。
- 无新依赖、索引服务、缓存框架、多级备用通道或新产品参数。

## 4. 证明与实际语义

### 4.1 三层空间严格区分

1. **原菜单的完整合法空间**：所有报价、规则套餐及合法餐内组合。
2. **已生成单餐候选池 `C_m`**：可能因 `maxMealCandidatesPerMeal`、套餐展开或资源边界成为上一层的子集。本方案只扫描实际保留在 `mealSets[m].candidates` 的候选。
3. **DP 中间状态空间**：又可能因营养桶合并和 `maxDpStates` 丢失前两层中的路径。本方案的见证绕过的是这一层的丢失，不能恢复第二层已经漏掉的候选。

若原菜单有预算内方案，但它使用的某餐低价候选在层一已被删掉，本方案可能找不到。不能说“原菜单没有预算内方案”，也不能因此把层一近似标记清零。

### 4.2 逐餐最低价组合为何合法且价格最低

当前源码在搜索前逐餐生成候选（4290–4301）。供应、售罄、单餐单窗口、套餐份量、含饭互斥及锁定都已包含在每个合法 `MealPlan` 中。跨餐重复、类别覆盖、口味、营养偏差仅参与评分，不是“跨餐不能同时选择”的硬约束；状态转移可独立从各餐候选中取一个。故当前全天合法空间正是这些池的笛卡尔积。

令 `P_m={c∈C_m | c.priceComplete}`，`p_m=min_{c∈P_m} c.knownPriceCents`。若每餐 `P_m` 非空，各取一个最小者得到 Q。Q 属于该笛卡尔积，锁定和其他单餐硬约束自然成立，价格完整，待选总价为 `p=Σp_m`。

对任意其他价格完整组合 X，每餐均有 `price(X_m)≥p_m`，所以 `price(X)≥Σp_m=p`。已吃价格完整且支出 S≤预算 B 时，真实可用余额 `R=B−S≥0`，因此

`池内存在价格完整预算内组合 ⇔ Σp_m≤R`。

若某餐没有价格完整候选，则池内不存在**可核算**的全天预算内组合。未知价可能最终真实很低，但当前不能以此出具预算内证明。不能把未知价的已知小计零作为最低价候选。

这里不证明原菜单全局存在性，只证明这些固定池中的命题。若以后增加跨餐硬性不重复、菜品总库存或共享购买数量限制，上述笛卡尔积前提会改变，逐餐最小值不能直接沿用。证据中的 2×2 假设反例说明这个前提的必要性，**当前产品并没有该跨餐硬禁令，不建议为假设新增校验或功能**。

### 4.3 与三策略比较器的关系

固定参考 `IsPlanBetterForStrategy` 先比较预算可行性，再比较营养完整性，再进入 primary/economy/taste 的各自主序（1366–1372）。已评估的 Q 满足 `overBudget=false`，所以对于每个请求策略，它都严格优于任何 `overBudget=true` 的 DP 终端候选，与后者营养/口味/价格得分无关。

将 Q 与原终端候选集合一起送入**原比较器**，各策略最终选中者必须预算内。若 DP 已经找到更好的预算内方案，原比较器仍保留它，不强制最低价见证胜出；economy 也先比较营养 tier，因此最低价见证本身不等于 economy 全局最优。按现有规则从更大的终端集合择优，输出在该规则下不会比未加入见证的 DP 结果更差，但这不是每个单独指标都改善的 Pareto 承诺。

若多个策略最终选中同一见证，沿用现有 planKey 去重和 `offeredAs` 合并，不能为了“有三套”重复造方案。

### 4.4 营养完整性、锁定与已吃记录

自动新增报价在 `CollectWindowEligibleOffers` 中经过四项完整性门槛，未知营养未锁定不得新增（807–812）。每餐的锁定项固定放入所有候选（937–981 及后续候选工作项初始化）；营养累加的 `has*` 用 AND 传播，不能被后续已知项“补成已知”。因此第 m 餐每个候选的营养完整性都等于该餐固定锁定项完整性的合取；已吃记录对日总和的完整性影响也对所有组合相同。

所以同一请求内所有全天组合营养完整性相同：若存在营养完整预算内组合，Q 也完整；若固定锁定项或已吃记录使营养不完整，Q 和其他方案都仅供参考，不能声称达标。无需再扫描两种完整性类别，也无需额外“更完整方案备用”结构。这是现有候选资格规则的结论，不是让新代码再校验一次所有营养。

锁定价格已计在每个候选的 `knownPriceCents` 中，扫描不应再次加锁定费用。锁定价格未知会使相关候选价格不完整，无法给出预算内见证。已吃支出只在 `R=B−S` 扣一次，不能再加进 Q 的待选总价。

已吃价格未知时，不论 Q 的待选价格多低，都不能保证全天预算内；保留 A03 的 `BUDGET_ACCOUNTING_INCOMPLETE` 语义，本方案直接不出具预算内见证。未设置预算时本方案不运行；预算恰为零仍是有效预算，不能用真值判断把 0 当未设置。

## 5. F5、searchComplete 与文案

### 5.1 F5 保留启发式，撤回笼统营养界

这份见证只提供预算可行性，不限制营养偏差、口味损失、多样性损失或最终 planKey 大小。A01 的 F5 中两种组合总价都为 200 分；即使设预算 200，逐餐最低价平局时保留原枚举第一项，仍可能选到局部近、全天偏差 **3999 bp** 的组合，完整池中偏差为 0 的另一组合并不会因价格见证自动恢复。

以上是对既有两组合的手算，不是已实施新 DP 的运行结果。它足以说明最低价证明无法推出 `M×营养步长` 的全局损失界。A01 的 764/765 bp 上界反例仍有效。准确口径应为：

> DP 桶化/截断后为启发式近似。新增最低完整价见证可在明确前提下保留已生成候选池内的预算可行性；尚无覆盖全局丢桶及三策略整体排序损失的统一近似误差保证。局部营养界仅适用于对应代表路径未被丢失的桶内替换。

不要为修这个预算问题增加逐桶双代表、多维保护层或重做整套 DP；它们既非必要，也没有自动补足 F5 的全局证明。

### 5.2 输出行为和前端说明

实施时保留 `searchComplete=false`、`maxDpStates` 的 `capsHit`、`APPROXIMATE_DISCRETIZATION` 和 `SEARCH_LIMIT_REACHED`。从原候选池直接取出的见证也用当前 tracker 经正式评估，表示整次搜索未证明最优，不能因这份最低价证书清除算法近似信息。

在原 F6 那种“池内预算内方案被 DP 删除”的请求中，加入见证后，各策略应选预算内方案；正常状态汇总应由 `NoFeasibleWithinBudget` 转为 **`OkPartial`**，因为截断标记仍在。不是 `Ok`，也不是“精确最优”。这只是方案设计预期，尚未修改/运行新生产实现。

不新增结果字段、见证专用徽标或额外用户流程；这些文案仅作为后续实施卡的准确说明，不在本卡修改前端。

## 6. 已超预算且后续免费：具体前提缺口

主 PRD §3.2 要求已超预算时明确预算内无解。固定参考却使用 `remainingBudget=max(0,B−S)`，再以 `plannedPrice>remainingBudget` 判断超预算（1289–1301）。当 S>B 且待选价格为 0，比较变为 `0>0`，得到 false；这不等价于真实全天条件 `S+plannedPrice≤B`。

本卡用固定 A03 CLI 实测，价格与营养均为显式合成数据、价格 0 为已知零：

| B | 已吃已知 S | 待选 P | 当前核心 overBudget / 状态 | 真正全天判定 |
|---:|---:|---:|---|---|
| 100 | 100 | 0 | false / OkPartial | 100+0≤100，成立 |
| 100 | 101 | 0 | **false / OkPartial** | **101+0>100，不成立** |

证据：`known-spend-100-free-option.*.json`、`known-spend-101-free-option.*.json`。原生请求包含正常记录元数据与已知价格/营养快照；没有通过把未知价写成零制造问题。

因此见证方案明确以 **S≤B** 为适用条件，S>B 时不新增“预算内见证”。这不是兜底框架，而是预算命题的必要语义边界。它也不会自动修正原 DP 对免费余餐的现有误标；若后续要求“已超预算”的全部输出也闭合，应由 P01 将该实际判定问题纳入明确修复范围，不能只加最低价见证就宣布所有预算边界已修完。本卡不代改预算规则或另派任务。
