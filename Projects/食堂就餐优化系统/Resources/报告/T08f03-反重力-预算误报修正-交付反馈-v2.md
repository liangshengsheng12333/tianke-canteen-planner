## 0. 一页结论

- **缺陷根因定位**：
  1. `domain/plan.ts:budgetFromPlan` 与 `planBudgetInput` 原实现直接提取方案整日全天总价（`plannedTotalKnownCents`，如 2750 分），完全未感知当日餐次已被确认记入 `logs` 或标记结束的事实；
  2. `domain/logs.ts:buildBudgetView` 在计算 `overBudget` 时，在餐次全部确认后，依然拿整日计划 2750 分去比对剩余可用 2250 分（5000 - 2750），导致已吃餐次被双重计费并触发假超支（2750 > 2250，误报超支 500 分）；且超支金额统一计算缺失；
  3. `domain/store.ts:refreshPlan` 在 `planningMeals.length === 0` 时早退并保留旧方案，而 `getHomeView` 未在全部确认时将 `planState` 置为 `'all-handled'`，导致 UI 仍以待规划状态展示旧方案。
- **根因级修复**：
  - `domain/plan.ts`：增强 `planBudgetInput(plan, day, catalog)`，引入待规划餐次（`planningMeals`）过滤。当全部餐次确认/结束时，剩余待规划开销精确归零（`plannedTotalKnownCents = 0`，`plannedTotalCents = 0`，`overBudget = false`，`withinBudgetKnownAmounts = true`，`overageCents = 0`）；部分确认时只计入待吃餐次计划金额；
  - `domain/logs.ts`：`buildBudgetView` 中仅在 `plannedKnown > 0` 且 `plannedKnown > remainingKnown` 时判定方案超支；统一超支额算法为 `Math.max(0, spentKnown + plannedKnown - budgetCents)`；实际消费已超全天预算且待规划为 0 时输出明确文案；
  - `domain/store.ts`：在 `getHomeView` 中检测待规划餐次为 0 时将 `planState` 设为 `'all-handled'`，提示“所有餐次都已确认或结束，本轮没有需要规划的餐次”，引导语更新为已全部处理状态。

## 5. 根因剖析与为什么不是防御性补丁

### 根因剖析（Data Flow & State Machine Mismatch）

1. **方案预算与就餐状态脱节**：
   原有 `interpretPlanResult` 仅通过 `plan.budget` 静态读取规划时的全日预算汇总（如 2750 分）。当用户执行 `confirmMeal` 将某一餐或全部三餐落库为正式消费时，数据库中的 `day.logs` 增加了实际支出，但 `day.plan` 仍然保存着包含该餐的完整计划快照。
2. **余额双重扣除（Double Counting）**：
   在 `logs.ts:buildBudgetView` 中：
   `remainingKnown = budget - spentKnown`（5000 - 2750 = 2250）；
   随后判定逻辑为 `plannedKnown > remainingKnown`。由于 `plannedKnown` 仍被赋值为全日方案 2750 分，导致系统拿“全天计划 2750”去和“扣除已吃后的余额 2250”进行比对，直接得出超支 500 分的荒谬结论。
3. **状态机终态缺失**：
   当用户三餐全部处理完成时，`planningMeals(day, catalog)` 返回空数组。`store.refreshPlan()` 内部虽然拦截了空请求，但并未改变 `HomeView` 的 `planState`，使得主页仍认为当前存在有效计划，持续执行该比较。

### 为什么这是架构级根因修复，而非表面防御打补丁？

- **动态投影而非魔法值覆盖**：
  在 `domain/plan.ts` 中，`planBudgetInput(plan, day, catalog)` 严格基于领域模型 `planningMeals` 进行动态投影过滤。如果餐次已经确认或结束，它就不再属于“待规划/待就餐”范畴，其计划开销在逻辑上自然为 0。这符合领域真实世界事实，不是在视图层粗暴写死 `if (allConfirmed) planned = 0`。
- **部分确认无缝衔接**：
  本方案自然支持“吃一餐、算剩余”的渐进式就餐。当吃了早餐（550 分）时，剩余未吃计划动态变为午餐+晚餐（2200 分），用户无需强行点击“重新生成方案”，当前界面上的预算就已是正确的 2200 <= 2450，彻底杜绝了“吃完早饭看一眼首页就吓一跳说超支”的恶性体验。
- **超支公式数学严谨性**：
  统一超支额计算公式为 `Math.max(0, spentKnown + plannedKnown - budgetCents)`。无论是已花超标、计划超标、还是两者之和超标，均能统一给出唯一的、数学上精确的超支分值，不再依赖片面的 `plannedKnown - remainingKnown`。
