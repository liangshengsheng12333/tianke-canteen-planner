## 3. 改动与等价性理由

1. **精确去重索引。** 以原支配判定的必要键（四项精确营养、完整位，非终端另含分类掩码）计算查找槽；只跳过必不可能支配的槽。链节点按原 `nextLayer` 下标追加，保留第一次匹配及原地替换次序。支配成立必有相同必要键，替换不改变槽位置。哈希相同不视为状态等价：原 `DpExactDominates` 的完整频次重建、价格、重复对、未知分类、偏好、终端类别覆盖与完整 key 比较全部保留。非终端频次没有压缩成粗营养 key。
2. **桶索引与稳定排序。** 桶键仍是原20 kcal/50 dg整数除法及完整位。碰撞仍精确核键；同桶仍只有严格较低启发式分数才替换。排序使用缓存分数的稳定归并排序，相等分数取左侧，等价于原稳定插入排序的出现顺序；保留的桶、限额、预算见证和 capsHit.observed 均不变。
3. **完整 key 按需及单餐行复用。** 只有原终端五项指标全相等、确实走到 key 决胜时才计算并缓存状态摘要。每单餐候选仍由原 `WritePlanKeyRows` 序列化为完整动态缓冲；按原早/中/晚顺序移除单餐数组的外层括号并拼接，SHA-256 仍覆盖完整规范 JSON，无4096字节或其他截断。新转移清空摘要有效位；所有权在本次请求内。
4. **终端完整评价筛选。** 终端状态已有相同增量累计的营养、价格、类别、重复对及偏好。用这些值建立无 key 的轻量比较记录，调用原三策略比较器：仅当每个现任方案在 key 决胜之前已严格胜出，才跳过该终端的完整评价。指标平局或任一策略可能改善时，仍走原 `EvaluateFullDayPlan` 和完整 key 比较/保存。因此预算内最低价见证、三策略差异、最终排序及输出 flags 未另起实现。完整输出在真实 G1/G2/G3 和37组反例中逐字节一致。

cap256、单/双餐DP20000、三餐DP32、nodes200000以及正式请求 wallClockMs=null 全部保留。没有禁算法、减餐、缩菜单、改目标、改截断策略或把正deadline当正式矩阵。

用每阶段生成数Q、原始保留数R、桶数B、哈希链实际扫描数E表示：原去重/桶扫描/插入排序具有 O(QR + RB + B²) 的二次项；新查找为 O(Q+E)，排序 O(B log B)，外加原精确频次比较和必要完整SHA成本。**哈希碰撞或同必要键不可支配状态很多时，E最坏仍可二次增长；不宣称理论最坏已线性。** 单餐行缓存占用完整行总字节；索引/排序额外空间 O(R+B+H)，H至多65536槽，槽数只影响碰撞率、不限制状态数。

临时索引/排序用阶段Arena；状态和key缓冲仍由请求Arena持有，索引指针不逃逸。原生阶段结束释放临时块；WASM原bump分配器只退役块，全部输入/结果释放后才整体复位，阶段释放**不代表WASM页数即时下降**。新增索引使G2峰值从505增到562页，已如实记录。未改mp_alloc/mp_free或平台生命周期。
