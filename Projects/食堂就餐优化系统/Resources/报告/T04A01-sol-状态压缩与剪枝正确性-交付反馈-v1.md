## 3. 实际比较器及 DP 无损支配定理

### 3.1 重建实际排序

源码 `IsPlanBetterForStrategy`（1335–1422）先比较可用性，再在设置预算时优先 `overBudget=false`，随后营养完整方案优先。令 `D=(-categoryCoverage,repeatedDishCount,unknownCategoryCount)`，`P=(!priceComplete,knownPriceCents)`，数值越小越好，则完整方案的实际策略主序为：

| 策略 | 实际词典序（以上共同前序之后） |
|---|---|
| primary | `(deviationBp, D, -preferenceScore, P, planKey)` |
| economy | `(tier, P, D, -preferenceScore, deviationBp, planKey)` |
| taste | `(tier, -preferenceScore, D, P, deviationBp, planKey)` |

不完整方案跳过 `tier/deviationBp` 的比较。未知价格不是零价格：先比较价格完整性，再比较已知金额和。营养数值有各自 `has*` 位，`AddNutrition` 以 AND 传播完整性并累加已知和（391–399）；只要前缀不完整，后缀不能把它恢复完整。

**契约一致性待裁定：** 冻结 v1.2 §10 及继承 v1.1 的 economy/taste 摘要未列出末尾额外 `deviationBp`，源码却在 1374–1376、1397–1399 比 `planKey` 更早比较原始偏差。本专项按照**实际源码**分析和枚举，没有擅改规范；不能以“同 tier”默认直接比哈希。缺失预对齐裁定是否曾允许该额外键，当前无法核实。

### 3.2 在什么条件下精确支配成立

同阶段前缀 A、B 的未来候选集合相同：单餐候选先生成，跨餐转移不受前缀价格、口味或历史选择改变。假设状态中保存的量与终端评价语义一致且无溢出/容量丢失，非终端要求：

1. 四项营养数值相同、营养完整位相同、**待选部分**价格完整位相同；
2. `catMask` 相同，完整底层单品频次向量相同；
3. A 的金额、重复对数、未知类别数不大于 B，口味分不小于 B，并有至少一项严格改善。

对任意同一后缀 R，四项和按相同增量变化；完整位同 AND 同一个后缀；分类覆盖均为 `popcount(mask OR mask_R)`；口味、金额、未知类别计数加相同增量。重复对数满足

`rep(A⊕R) = rep(A) + rep(R) + Σ_d count_A(d)·count_R(d)`。

频次向量全同使跨餐新增项相同。金额较少且完整性相同不能使预算可行性变差；其余所有参与排序的指标均不变差。至少一项真实比较指标保持严格改善，所以三策略在到达 `planKey` 前就已严格决定 A 更优，删除 B 安全。对完整性为 false 的情形，未来都继续为 false，营养偏差被两侧一起跳过，论证仍成立。各 `has*` 位不全同而总 `nutComplete=false` 不自动构成缺陷：本比较器并不比较不完整方案的单项偏差。

这里需要**分类位掩码**，不能只保留当前覆盖数：相同覆盖数的不同类别，后续 OR 后覆盖数可能不同。也需要完整频次，不能只保留当前重复数。已吃记录的营养参与日总和；已吃记录单品不进入本实现的待选方案多样性，所以初始频次为零与当前终端语义相符。

非终端四个改善指标全部相等时，源码 2072 返回 false，**没有**按前缀 ID 或前缀哈希丢状态。这是正确的保守选择：SHA256 的最终大小顺序不具有前缀单调性。源码 1807–1808 关于“前缀字典序更小就无损”的注释并不成立，也不代表实际已执行该错误剪枝。

终端不再有后缀，分类只需比覆盖数；其余同等数值条件下，Pareto 严格改善仍安全。全指标相等时，源码按完整规范元组哈希裁决（2099）。对静态短 ID，序列化顺序、合并数量、offerId 排序与正式 `BuildPlanKey` 一致；一餐最多 8 项、至多 3 餐、静态 ID 最多 64 字节，使用量低于 4096 字节，16 对项目缓冲也足够。

**成立条件没有被现实现全部满足**：F1 是价格状态语义错误，F3 是频次丢失，F4 是与终端重复数容量语义不一致。不能把上述带前提定理直接当成当前全部输入的正确性证明。

### 3.3 F1：已吃未知价使 DP 错误支配

证据前缀：`dp-intake-price`，**1 餐、2 个候选**；无预算、无任何截断。早餐已吃手动记录营养为四项已知零，价格未知；只规划午餐。两候选营养都为日目标 `(2370,840,711,3485)`，类别/重复/口味相同，A 价格未知，B 价格已知 100 分。

实际比较器应选 B：营养相等，价格完整优先。实际 DP 选 A，`priceCents=null`，`searchComplete=true`、`capsHit=[]`。独立枚举选 B；BnB 在这个单餐例没有非叶剪枝，也选 B。

根因：初始 `priceComplete=intake.priceComplete=false`（2144），之后 AND 候选（2182），A/B 状态价格位都变 false；DP 误把 A 的已知和 0 当低价优势，删掉 B。正式 `EvaluateFullDayPlan` 却从 true 重建**待选部分**完整位（1172–1208），不含 intake。状态与终端不是同一个量。

最小修正方向：DP 与 BnB 根的待选价格完整位初始化为 true；已吃记录完整位单独保留用于预算核算。不要取消“价格完整优先”或把未知价格填零。需复查：已吃价格未知/已知两类，候选价格未知/已知，有无预算及三策略；本卡未修改。

### 3.4 F3：64 项频次表遗漏可供选择的菜

证据前缀：`dp-untracked-dishes`，**2 餐、2×1 个候选**，目录 66 个菜，前 64 个无报价，最后两个是实际供餐菜 A/B。午餐可选 A（100 分）或 B（200 分），营养都为午餐参考；晚餐只能选 A（100 分）。

两全天方案营养偏差同为 2003 bp，类别覆盖相同；按 primary，B+A 的重复对数 0 优于 A+A 的 1，应先于价格比较。DP 实际选 A+A（200 分），独立枚举与 BnB 选 B+A（300 分）。DP 报 `searchComplete=true`、无近似标志，仅评估 3 个状态。

根因：`DishIndexTable::Build` 只取目录前 64 项，A/B 的 `IndexOf=-1`，转移直接跳过它们的频次/重复更新；两个午餐状态被误判为频次相同，便宜 A 支配 B。目录解析器 825–832、942 接受这些菜，并无 64 菜的入口拒绝或资源近似记录。增加无供餐条目也能改变算法正确性，说明不能把此表当安全压缩。

最小修正方向：按本次候选涉及的全部底层单品建立完整映射和足够宽的计数；若暂时固定容量，必须在入口明确拒绝或安全停止使用相关支配，不能静默省略。需连同 BnB 共用状态检查计数宽度及套餐展开；B&B 忽略部分重复通常会降低下界，但不能据此让 DP 使用不完整等价键。

## 4. BnB 乐观界：正确部分与失败前提

### 4.1 可采纳性的逐项证明

假设前缀字段忠实表示最终评分量，整数计算不溢出，候选池固定且每个非空餐次的后缀界覆盖所有候选。`ComputeSuffixBounds`（2422–2493）对每餐取营养各维最小/最大，再跨餐相加，因此任一叶子 X 的营养落在前缀加后缀区间。目标到该区间的距离不大于到 X 的距离。对非负权重，`round_half_up` 单调，故加权求和的 `lbDeviationBp≤dev(X)`，正 tier 宽下 `floor(lb/W)≤tier(X)`。

价格已知和用逐餐最小值之和，下界成立；`anyPriceComplete`/`anyNutComplete` 是每餐存在一个完整候选再跨餐 AND，给出“可能完整”的乐观位。不同维极值不能由同一方案同时取得，只会使界更乐观，不会破坏可采纳性。若乐观价格完整且最小已知价仍严格大于剩余预算，那么子树必不可能预算内；**等于预算仍可行**，源码采用 `>` 是正确方向。已吃价格未知时所有方案预算核算都不完整，应统一进入相同预算前序，不能因此污染之后的待选价格比较。

分类并集 OR 是覆盖数上界；口味逐餐最大值之和是上界；未知类别逐餐最小值之和是下界。若使用同一个完整底层单品统计口径，跨餐重复非负，故 `prefix.rep+Σ suffixMeal.minRep` 为最终重复数下界。

用这些量构成虚拟理想向量 O，按各策略**真实字段顺序**比较。当第一个不等字段已经严格劣于 incumbent，O 及任何真实叶子都不可能胜过 incumbent，可剪；若 O 某字段更优则不能凭后续字段剪。源码依此顺序逐字段返回，economy/taste 也包含实际末尾偏差键。预算和营养完整性同理；当乐观完整位为 true 而实际叶子不完整时，乐观方案在更早的完整性维度已占优。

所有非键字段相等时 `CanPruneForStrategy` 返回 false，不假设 planKey 下界；只在**全部请求策略都可剪**时丢分支（2801–2817）。这正确保留哈希平局、多个策略的不同最优解。节点上限触发会另标不完整；本次未把限额中断算成剪枝证明。

### 4.2 F2：错误价格完整乐观位剪掉同 tier 更低价

证据前缀：`bnb-intake-price`，**2 餐、2×1 个候选**，仅请求 economy，无预算；早餐四项已知零但价格未知。午餐 A=`(948,336,284,1394)`、200 分；B 仅能量比 A 多 1 kcal、100 分。晚餐固定=`daily−A`、100 分。

完整枚举：A+晚餐偏差 0、tier=0、300 分；B+晚餐偏差 1、tier=0、200 分。economy 应选后者。BnB 先访问午餐更贴近参考的 A，取得 incumbent，再把 B 分支剪掉：`optPriceComplete=false` 与 incumbent 待选价格完整 true 对比，被误认为“价格完整性必劣”。实际返回 300 分，`searchComplete=true`，评估 3 个节点；独立枚举和 DP 返回 200 分。

根因/最小修正同 F1：2901 将 intake 完整位初始化到待选状态；2520 的 AND 无法恢复 true，2601–2603 给出非乐观位。不要把此问题归咎于偏差区间下界、同 tier 设计或等界剪枝；这几项在此例均非根因。

### 4.3 F4：底层实例超出终端 128 容量时，“重复下界”变成高估

证据前缀：`bnb-bottom-item-cap`，**2 餐、2×1 个候选**；只有 16 个目录菜，避开 F3。午餐两个固定套餐有完全相同的营养、价格和 13 个组件，每组件 count=10；B 套餐名称命中一个口味词，A 不命中。晚餐固定一个其他单品；请求 primary，无 intake/预算/截断。

按完整单品统计，午餐重复对数为 `13×C(10,2)=585`，两方案相同，B 应以口味 1 胜 A 的 0。正式终端平铺数组却只保存前 128 个底层实例，实际报告两者重复数均为 `12×45+C(8,2)=568`；B 仍应胜。这个最优选择不依赖采用完整还是现有截断口径，因为两者重复数始终相等。

BnB 前缀频次累计了全部 130 实例，得到 585。先访问 A 后，B 分支的重复数下界为 585，超过 incumbent 终端 568，于 2588–2590 错剪，未走到口味比较。实际返回口味 0 的 A，`searchComplete=true`、无 caps、3 个节点；独立枚举及 DP 返回 B，口味 1。完整枚举还记录 `bottomItemCount=131`、`fullRepeatedPairs=585`，避免把终端截断当数学上的重复定义。

输入已被实际 CLI 接受：固定套餐组件条数未设同等上限，单组件 count 在 1..10 内（catalog.cpp 182–220），`maxItemsPerMeal=1` 限制的是套餐购买项，不是展开实例数。该例是容量边界反例，**不是首批真实菜单实测**，不推断出现概率。

最小修正方向：终端、单餐及搜索状态统一使用完整频次统计来算重复对数；单餐同样存在 64 实例数组（617–679），终端是 128 实例。不能只把 BnB 下界改成 `min(rep,128)`，因为 128 是实例数而非重复对数上限。若需固定规模，入口须明确校验真实展开规模，并与产品支持范围一致。需定向复查：跨餐同菜、套餐 count、64/128 实例边缘、计数宽度及全策略；本卡没有自动修复。

## 5. 桶化和截断：可成立的局部界与反例

### 5.1 局部界的严格表述

营养是非负整数，桶号为 `floor(x/Δ)`。同一桶两个真实累计量满足 `|x−x'|≤Δ−1`（采用较松的 `≤Δ` 也正确）。这一步没有把数值改成桶中心，只是换了代表方案。

跟踪某个精确方案的对应路径：在每一阶段，其延伸状态都必须仍能找到同桶代表，**且该代表不会被全局截断删除**。后续候选转移只作相同加法，则由三角不等式，经过 r 次代表替换，各维差值至多 `r(Δ−1)≤MΔ`。精确支配替换若已满足第 3 节前提，不增加营养误差。这个归纳证明保证的是“存在一条对应近邻路径”，不是任意两个最终返回方案都很近。

若目标正、权重非负，设 `α_n=10000w_n/(1000T_n)`，`round_half_up(z)=floor(z+1/2)`，则

`|round(α|x−T|)−round(α|x'−T|)| ≤ ceil(α|x−x'|)`。

因为 `||x−T|−|x'−T||≤|x−x'|`，两个 floor 值的差至多为输入差的向上取整。因此营养完全可比时可用 `Σ ceil(α_n·MΔ_n)` 作上述对应路径的偏差差值界。**不能一般用 `round_half_up(αδ)` 代替 ceil**：例如两实数输入 0.4 和 0.8，输入差 0.4 四舍五入为 0，输出差却为 1。源码注释 1816 已用 ceil，作者交付反馈 §3.2 用 round，两处口径不同；修正取整仍解决不了全局丢桶问题。

若要把路径界提升为返回 primary 方案相对于精确最优的偏差损失界，还须保证对应路径保留营养完整性、预算可行性等更早排序前提，使它能与原最优处在同一比较层。economy/taste 的价格、口味、多样性和分档也不会因营养界自动获得误差保证；同 tier 内原始偏差可能让位于这些指标，不能直接套 primary 的标量最优结论。

### 5.2 F5：全局丢桶使对应路径归纳断裂

证据前缀：`dp-global-bucket-drop`。午餐 A=`(948,336,284,1394)`，B=`(0,0,0,0)`，晚餐固定为全天目标 `(2370,840,711,3485)`；价格均 100 分，所有菜不同但类别同 other，无预算/口味。两种全天组合可手算列全：

| 午餐 | 全天营养 | 偏差 bp |
|---|---|---:|
| A | `(3318,1176,995,4879)` | 3999 |
| B | `(2370,840,711,3485)` | 0 |

`maxDpStates=1`。午餐两状态属于不同桶，A 的前缀启发式更好，排序后只保留 A，B 的桶整桶消失。下一餐只能得到 A+晚餐。实际 DP 偏差 3999、`searchComplete=false`，明确记录 maxDpStates 与近似；独立枚举与 BnB 取偏差 0 的 B+晚餐。

代入 `M=2`、步长 `(20,50,50,50)` 和真实目标：作者 round 公式为 764 bp，ceil 版本为 765 bp，均远小于 3999 bp。此例没有同桶替换误差，损失完全来自**丢桶**，故“桶内界”无法推出该实现的全局近似比。源码 1811–1816 和作者报告的笼统上界说明应撤回或补足前提，2263–2265 的局部替换本身不构成反例根因，2290–2297 的保留前 K 个桶才使该证明断裂。

最小修正方向有两类，应由后续执行卡选取：保留现算法但准确报告“启发式状态截断，没有已证明全局误差上界”；或设计有覆盖半径/证书、可行性与策略指标保护的近似方案，再单独证明。不能只改步长/增大默认 K 就宣称界已成立。

### 5.3 F6：同桶零营养误差仍能破坏预算可行性

证据前缀：`dp-same-bucket-budget`，**1 餐、2 候选**。营养都精确等于日目标，预算 100 分；A=101 分、口味 1，B=100 分、口味 0。两者互不 Pareto 支配，随后同桶合并。

启发式评分 2105–2107 为 `dev×100 + price/10 + rep×50 − coverage×30 − pref×20`；价格整数除 10 后都为 10，A 因口味更好取代 B。DP 实际返回超预算 1 分的 A；完整枚举及 BnB 返回预算内 B。两者营养误差为零，且合并后只有一个桶，所以即使取消最终丢桶步骤也会发生。

这说明必须区分：营养接近、预算可行、各策略的序关系、最终哈希四个不同性质。现实现已诚实标近似，不能将本例等同于 F1–F4 的“无截断仍错误”；但不能把营养误差界作为它的预算或整体品质保证。若产品需要“有预算内方案就保留一个”，需明确增加预算可行性保护及剩余餐次可扩展性的证明；仅在当前前缀按价格设桶仍不能证明未来可行性。

## 6. 定向实验汇总与剩余缺口

每个实例的完整全天组合数均为 2；基础字段和 nutritionConfig 取既有冻结夹具，菜/报价/状态均在专属脚本内替换为可手算合成数据。独立枚举直接列出所有报价组合，以明确整数公式、词典序元组和 Python 标准库 SHA256 决胜，不调用生产函数；另一算法只是辅助对照，不当真值来源。各请求都只买一项/餐，因此层一候选可直接逐项核对，无套餐选择组合遗漏。

| 定向实例 | DP 对照枚举 | BnB 对照枚举 | 当前源码实际观察 |
|---|---|---|---|
| dp-intake-price | 不一致 | 一致 | DP 未限额错删价格完整方案 |
| bnb-intake-price | 一致 | 不一致 | BnB 未限额错剪 200 分同 tier 最优 |
| dp-untracked-dishes | 不一致 | 一致 | DP 未限额返回重复 1，而最优重复 0 |
| dp-global-bucket-drop | 不一致，有近似标记 | 一致 | 丢桶偏差损失 3999 bp 超过宣称界 |
| dp-same-bucket-budget | 不一致，有近似标记 | 一致 | 同桶误差 0，预算内方案丢失 |
| terminal-plan-key-tie | 一致 | 一致 | 所有非键分数平局；两前缀都延伸，终端取真实更小 planKey；BnB 4 节点，DP 4 状态 |

七个实例先在来源匹配的旧 CLI 运行，再用当前源码单独重建 CLI 复核，14 对响应逐字节一致；只重跑了这组定向实验，没有跑作者全量测试。**不把表内局部一致计为全算法/全规模通过。**

尚未确认的边界：

1. `ComputeTerminalDpPlanKeyHex` 使用 4096 字节缓冲，`overflow` 置位后未检查（1861–1902、2016–2018）。静态 64 字节 ID 可证明在容量内；规则展开 ID 是 `ruleId#dishId+...`（catalog.cpp 491–503），长度可超过静态 ID 上限。当前没有覆盖所有合法多套餐元组的长度证明，本卡未构造长键运行反例。后续应复用正式规范序列化/哈希或显式处理超长，不能仅凭短键算例声明所有 planKey 等价。
2. `dishCounts` 使用 u8，固定套餐组件加锁定数量可使真实频次超过其可表示范围。F3/F4 反例不依赖 u8 回绕；本卡未运行回绕专项，不声称该边界通过。完整映射修正应一起证明最大计数范围。
3. 缺失预对齐裁定及 economy/taste 末尾偏差键差异仍需 P01 定义唯一排序口径；不把现有实现推理替代产品决定。
4. 未做 WASM/前端/真机、性能、内存泄漏、全输入规模或一般异常路径验证；这些仍归后续集中测试/P09。

## 7. 交接影响与最小下一步

本次四类精确路径错误直接影响 T04“精确最优”声明，建议在新三算法核心接入前安排**单独修复卡**：先分离待选价格完整位；再统一完整底层单品频次/重复统计与明确支持规模；修复后绑定新源码/原生/WASM身份，复跑本报告相应最小反例并补受影响范围的独立验证。不能把旧候选 `searchComplete=true` 当最优证书。
