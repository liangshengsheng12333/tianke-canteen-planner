# 天科食客｜双模式界面设计方案

版本：P01-v1｜2026-10-20（Asia/Shanghai）  
作者：P01。本次仅设计，不修改业务代码，不派发外部执行任务。  
状态：用户已确认总体方向；本文件的具体页面、视觉参数和展示规则待用户查看，不冒充已实现或已验收。

## 1. 问题与目标

现有界面把档案、方案状态、逐菜操作、营养明细和维护工具连续展开，文字与按钮竞争注意力。用户认可业务功能，但认为臃肿、密集、文案绕，要求保留功能、提供简易与完整模式，并参考小米系统的柔光玻璃质感。

本次目标：让用户先看明白“这顿吃什么、去哪买、多少钱、搭配怎样、大概多少热量”，需要时再展开精确数值和高级操作。两种模式都清楚、漂亮、文案直白。

当前定位为日常健康饮食助手。服务人群可以扩展，个性化自动目标继续遵守既有适用性规则；界面改版不扩大核心已批准适用范围。

## 2. 已确认范围与本方案选择

| 项目 | 处理 |
|---|---|
| 当前饮食目标 | 均衡饮食、减脂控重；分别沿用现有 maintain、fatLoss 能力 |
| 训练偏好 | 个人资料中的独立选项，可以与上述目标组合 |
| 增肌 | 下个版本待办，本版不放可用或诱导点击的增肌入口 |
| 界面模式 | 简易、完整；建议默认简易，可自由切换并记住选择 |
| 正式营养与规划 | 复用同一份核心结果，不在两个模式各实现一套规则 |
| 数据 | 档案、菜单、预算、计划、记录、锁定和售罄共用；模式切换只影响展示 |
| 维护工具 | 收到“我的”内，和日常看菜单、选菜明确分开 |
| 业务范围 | 保留已有功能，不新增账户、社区、后台服务、付费或发布流程 |

## 3. 信息架构

底部三个入口：**今日 / 记录 / 我的**。

- 今日：选餐与本餐摘要，查看三餐，必要时自己挑菜。
- 记录：已吃记录、修改、撤销、补记及日期切换。
- 我的：资料与目标、预算和偏好、界面设置、菜单与备份；开发工具在独立次级入口。

用户浏览菜品、查看价格和自己选菜属于正常用餐，不藏进维护入口。菜单文件导入、原始数据和诊断才属于次级工具。

## 4. 今日页

### 4.1 共用布局

1. 顶部：天科食客、简短日期、轻量目标标签。目标标签可进入目标设置，不重复展示整份身体档案。
2. 本餐推荐：展开当前选中的待处理餐次，另两餐以简短摘要保留可达入口。时间仅作提示，不自动判定用户已吃或结束。
3. 今日小结：已记餐次、饮食进度与预算摘要。用户未设预算时不摆放空预算卡。
4. 每餐详情：完整菜品、份量、来源、锁定与售罄等操作。

同一语义的估算提示不要在标题、标签、说明和每个按钮旁重复四遍；保留一处清楚的餐级提示，食物详情仍可查来源。

### 4.2 简易模式

本餐卡优先顺序：**餐次和窗口 → 菜名与价格 → 搭配概况与约计热量 → 主要操作**。

以下为排版示意，所有菜名、价格和数值均为虚构示例：

```text
天科食客                         均衡饮食
今天 · 周二

午餐                         二楼 · 家常菜
鸡腿 + 时蔬 + 米饭                  ¥13

约 620 千卡
主食、蛋白质食物、蔬菜都有
营养为估算值                  看这餐详情 ›

[ 换一份 ]                 [ 确认吃了 ]

早餐  已记录                         ›
晚餐  查看推荐                       ›

今天已记 1 餐               看今日小结 ›

       今日       记录       我的
```

“确认吃了”打开简短确认区，核实吃了哪些、份量和实际花费后才保存记录。选择推荐或查看卡片本身不记账。

“换一份”保留同窗优先和硬约束；“自己选菜”放餐次详情的清楚入口。锁定、售罄、结束餐次等放对应餐次的更多操作，不能把不同餐次的操作混在一起。

### 4.3 完整模式

沿用相同餐卡和操作位置，在卡片下增加一个紧凑的“这餐的营养”区域，不复制整套首页。

```text
这餐的营养                         约 620 千卡
蛋白质         32 克                   …%
脂肪           18 克                   …%
碳水           82 克                   …%
                  热量来源比例

今日进度与预算                     展开 ›
```

以上数值仅用于展示排版，不代表目标、实际餐单或经校验的比例；实现时必须用同一餐的真实核心数据生成一致的数值和比例。

采用三行数值配一条细分比例条，避免三只大圆环与多张嵌套卡。参考目标、偏差解释、来源等放详情；预算以一组短行显示，不将内部九字段全部直接铺给用户。

## 5. 营养信息与文案规则

### 5.1 简易模式的“营养程度”

本版用**食物搭配构成 + 营养信息完整性**表达，暂不创造“健康分数”“健康等级”或未经定义的达标结论。

- 根据菜单已知类别及已知套餐组成，说明有主食、蛋白质食物和蔬菜中的哪些类别。三类已明确时可写“主食、蛋白质食物、蔬菜都有”。
- 某类未出现且相关类别信息齐全时，可直说“这份没配蔬菜”等事实；类别缺失时写“搭配信息待补”，不能把未知当作没有。
- 类别齐全只表示结构信息，不表示份量、微量营养素或整天饮食已经均衡。
- 热量完整但来源为估算时显示“约 ×× 千卡”；热量不完整时显示“热量待补全”，详情保留已知小计及缺项，不把未知当零。
- “营养信息待补全”“含估算数据”是信息状态，不与搭配类别结论混为一个健康评价。

### 5.2 完整模式的比例

“比例”指蛋白质、脂肪、碳水的**供能比例**，显示标题用“热量来源”，不能把三者的克数占比当供能比例。

比例必须源自同一餐的核心营养数据，采用统一的既有 4/9/4 换算口径并明确分母；不以日目标的 composition 充当本餐比例，不从示意图抄百分比。展示换算如何落在现有接口/前端需在实现前明确，不新增一套营养推荐算法。本次仅批准设计内容，不通过本文件隐式修改冻结接口。

任何一种宏量数据缺失，暂不展示完整比例条，改写“营养数据不全，暂不显示比例”；已有数值仍可查看。已知量为零与未知数据要区分。

### 5.3 两种模式共同遵守的文案

| 内部含义 | 面向用户的表达示例 |
|---|---|
| 估算 | 营养为估算值 |
| 价格未知 | 这餐花费还没填，暂时算不准预算 |
| 超预算 | 比剩余预算多 ¥×；可换一份或调整预算 |
| 目标不可用 | 暂时不能按这个目标推荐；查看原因 |
| 搜索限额 | 这次计算没有找到合适方案；可调整条件再试 |
| 保存失败 | 没保存成功，原记录还在；请重试 |
| 无候选 | 当前条件下没有可选菜品；可检查售罄或锁定项 |

最后两类业务状态必须依据核心实际结果和诊断细分，不把“无解”与“尚未找到”写成同一个结论。

错误先说明发生了什么，再给一个可执行动作。完整模式也不用状态码、缩写和长句；技术字段只留开发入口。超预算、未知营养、目标不可用、失效锁定等关键反馈不能全部藏在“有两项限制”后面。

## 6. 记录与我的

### 6.1 记录

首屏显示日期、三餐的已记/未记状态与简短内容，点击记录才编辑。补记入口清楚可见，编辑、撤销与结束/重开按记录或餐次归属收纳。

简易模式先显示吃了什么与花费；完整模式增加营养数值。两者都保留未知状态、真实实付、历史快照与幂等规则，不为简洁省掉必要确认内容。

### 6.2 我的与设置

我的首屏展示资料摘要和当前目标；点击“个人资料”再编辑，避免一进来就是长表单。

```text
我的
个人资料与饮食目标                  ›
预算与口味偏好                      ›
界面模式                  简易模式  ›
菜单与备份                          ›

开发工具（次级入口，非主导航）
```

“菜单与备份”内分别进入导入菜单、导出备份、恢复备份，不把三个流程同时展开。预检错误、替换影响、取消与保存失败的反馈完整保留。

界面模式设置提供“简易 / 完整”和简短预览说明。切换后只改变展示，不刷新计划、不产生新记餐、不清空数据。编辑中的输入保留；无法保留时先完成或取消编辑再切换，不能静默丢失。

## 7. 视觉方案

### 7.1 色彩与材质

本方案主方向：**雾白背景、低饱和绿作为食物品牌强调色、少量暖色点缀、局部柔光玻璃**。借鉴小米系统的空间、材质和层级，不强制照搬橙色品牌色。

- 背景使用极浅冷灰白；推荐卡保持接近实色的明亮底，菜名与价格有足够对比。
- 柔光玻璃用于底部导航、少量顶栏与弹层；不在每张营养卡、每行文字后叠模糊。
- 主动作使用稳定强调色；危险色仅用于确有风险或破坏性的动作，不把普通未完成进度涂成满屏红色。
- 功能是否可用不能只靠颜色表达。低性能或不支持真实模糊时，保留相同布局的轻半透明材质；实际微信支持与红米滚动表现待实现验证。
- 原生或自定义导航由真实材质/安全区/触控表现验证后选择，不在方案阶段锁死四项原生 tabBar。

### 7.2 字体与间距

一个清晰的无衬线字体家族，通过字号、字重、对比和留白区分信息。优先系统字体；如使用 MiSans，另核对实际加载方式、许可、声明和包体，不在此阶段下载完整字库。

以约 375px 宽设计稿为参考，以下是初始设计值，不是微信实际渲染已通过的结论：

| 信息 | 建议字号/字重 | 角色 |
|---|---|---|
| 页面标题 | 24px，600–700 | 每屏一个主要标题 |
| 关键热量数字 | 28px，600 | 只突出本餐一个值，单位弱一级 |
| 菜名、价格 | 17–18px，500–600 | 一眼可读的主要内容 |
| 正文、主要按钮 | 15–16px，400–500 | 大众操作与说明 |
| 辅助来源、日期 | 13–14px，400 | 保持可读，不以无限缩字塞内容 |

正文行高约 1.5；卡片间距大于卡片内相关行间距；避免多层描边、连续标签、连续“标题—值”小表格。兼顾系统放大字体，允许换行，不截掉关键价格、错误或按钮。

## 9. 设计验收

- 首页主要区域先看得到餐次、窗口、菜品、价格、搭配概况与热量；身体档案与技术字段不挤占主区。
- 简易模式不铺宏量数值长表，完整模式用同一餐真实数值和正确供能比例；两模式重要异常均可见。
- 切换模式前后档案、计划、餐次记录、预算及锁定/售罄数据保持一致，未保存表单不静默丢失。
- 看菜、换菜、记餐可直达；维护与诊断退出大众常规导航，完整模式仍可找到高级业务能力。
- 不用机械“每屏最多三个按钮”限制所有场景；以每个任务区域一个主要动作、必要次要动作清楚可达为准。
- 有真实微信渲染截图；大字、长菜名、未知值、错误态、弹层与安全区均可读；1×1截图不算视觉证据。
- 红米实际验证玻璃/透明层下的文字、滚动与触控，没有测量不得宣称性能门槛已达标。
- 业务回归保持确认幂等、实付与计划价区分、未知不当零、预算不虚报、改撤与历史快照、跨日隔离、导入恢复的取消/失败保全。
