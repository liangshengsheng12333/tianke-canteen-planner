## 结果逐项核对

1. **两层独立 Oracle：核心结果有支持，候选集核对范围较窄。** `two_layer_verification.json` 与三份 DP/BnB/Greedy 原始响应显示：人工极小菜单计数为早餐 10、午餐 15、晚餐 15，全天笛卡尔积 2,250；DP 和 BranchAndBound 的 primary/economy/taste 三策略 planKey、偏差和价格与该证据记录的 Oracle 真值一致；Greedy 原始响应保留 `searchComplete=false`，符合近似算法定位。Python 脚本用独立组合枚举与比较逻辑，但第一层只将独立候选数量与 C++ `candidatesEnumerated` 对照，没有逐候选内容比对；第二层目标值从一次 C++ 初始响应的 `targets.daily` 读取。因此它支撑该固定目标下的优化结果比较，不独立证明目标计算或全部单餐候选内容一致。
2. **截断、长键与排序/剪枝反例：主要结论有原始输出支持。** cap=2 的原始响应为 `searchComplete=false`，记录了 breakfast/lunch/dinner 的 `maxDpStates` 命中及 `APPROXIMATE_DISCRETIZATION`。4097 输入的 DP/BnB 原始响应均成功并选出 `plan:6c2a0a4e…c6fd2cd`，Greedy 返回另一个方案且 `searchComplete=false`；4095/4096 请求及响应也在目录中。7 个排序/剪枝场景的 DP/BnB 原始响应均成功，选择的 offer 与汇总记录中的预期一致。
3. **截断标记的文字口径不一致。** 交付反馈与 `counterexamples/README.md` 写 `DISCRETIZED_SEARCH`；cap=2 原始响应中实际的方案 flags 是 `ESTIMATED_DATA`、`APPROXIMATE_DISCRETIZATION`、`SEARCH_LIMIT_REACHED`，`counterexamples_verification.json` 也记录这三个值。原始结果确有截断和近似标记，但文档引用的 flag 名称不准确，应由 P01 要求勘正。
4. **双端矩阵的 3 个 BnB 用例没有测试到 BnB。** 输入 `native_wasm/inputs/matrix-branchAndBound-primary.request.json`、`...economy...`、`...taste...` 的 `requestId` 分别为 `req-matrix-branchAndBound-primary`、`req-matrix-branchAndBound-economy`、`req-matrix-branchAndBound-taste`，包含大写字母。三份 Native 与三份 WASM 响应均为 `ok=false`、`INVALID_INPUT`、`fieldPath=$.requestId`、`requestId=null`，每份仅 197 B。两端错误响应相同，所以被双端汇总统计为 byte/semantic match，但这三项不构成三策略 BranchAndBound 矩阵测试。独立 Oracle 和 7 个专项反例仍分别提供 BnB 正常路径证据，故影响的是矩阵覆盖与“该三组双端运行成功”的表述。
5. **Offer 营养端点未执行成功路径。** `native_wasm/inputs/endpoint-offer-nutrition.request.json` 的 `requestId=req-offer-nut-check` 合法，但缺 `offerIds`；Native/WASM 原始响应均为 `INVALID_INPUT`、`fieldPath=$.offerIds`、`缺少必需字段`。它证明两端错误处理一致，不能证明 `offer-nutrition` 成功调用一致。任务要求的辅助端点成功路径尚缺证据。
