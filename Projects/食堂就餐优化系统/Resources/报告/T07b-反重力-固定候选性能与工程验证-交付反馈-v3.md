## 3. 宿主测试环境与测量方法

- **宿主处理器**：AMD Ryzen 5 5600U with Radeon Graphics（6 物理核心 / 12 逻辑线程，基准频率 2.30 GHz）
- **物理内存**：13.86 GB（测试期间空闲可用内存约 3.88 GB）
- **操作系统**：Microsoft Windows 11 专业版（版本 10.0.26300 Build 26300）
- **Windows 电源方案**：平衡（GUID: `381b4222-f694-41f0-9685-ff5bb260df2e`）
- **Node.js 运行时**：v24.19.0
- **MSVC 编译器**：Microsoft (R) C/C++ Optimizing Compiler Version 19.51.36260 for x64（Visual Studio 2026 Developer Command Prompt v18.11.0）
- **测量执行规则**：
  1. **完全单任务独占顺序运行**：在计时段内无并行构建、无微信开发者工具高负载、无其他测试/子代理并发。
  2. **冷热隔离与统计规范**：每个“组 × 算法 × 平台”固定执行 **1 次预热（warmup，不计入统计）** + **5 次计入统计的连续独立测量（Run 1..5）**。
  3. **分项互不混合**：
     - Native CLI 记录宿主总耗时（`hostTotalMs`，包含进程创建、文件读取、核心调用、文件写盘与进程销毁）；
     - WASM 分开记录纯核心耗时（`coreMs`，仅包裹 `exports.mp_plan` 调用）、桥接耗时（`bridgeMs`，含内存分配/数据进出拷贝/释放）与 Node 宿主总耗时（`hostMs`，含磁盘读取与写盘）；
     - 双平台数据严格分列，不混合计算综合平均值。
  4. **实验停止线**：单次 30 秒。本次 24 组实测全部在 **70 ms 内** 完成，零超时、零中断。

### 6.2 算法增长因素与真实菜单现象分析

1. **真实菜单与合成菜单的核心差异**：
   - 在合成极小菜单 G0 中，全部 5 道菜均具备完整确定的营养素，因而餐次候选集合完全展开（早 10、午 15、晚 15，笛卡尔积组合数高达 2,250 组）；
   - 在首批 T03d 真实菜单（G1–G3）中，当前仅有 4 道菜（原味肠粉、瘦肉肠粉、白切鸡饭、手抓饼）具备经批准的有依据估算营养，其余 31 道菜营养均为未知状态；根据 PRD 契约，营养未知的菜品不能作为自动规划方案的完整组合输入，因此单餐有效营养候选数被天然收敛（早餐 4 种组合、午餐 5 种、晚餐 5 种，全天搜索空间为 $4 \times 5 \times 5 = 100$ 种组合）；
   - 这客观解释了为何 G3 的 DP 状态数（$S=124$）和 BnB 节点数（$N=69$）反而远小于 G0（$S=1720, N=1510$）。
2. **耗时构成的解耦发现**：
   - G0 请求的 JSON 体积为 8.6 KB，WASM 核心耗时仅需 1.1 ms（Greedy）至 5.9 ms（DP）；
   - G1–G3 请求的 JSON 体积为 41.5 KB（主要由 35 道真实菜品、35 个 Offer 及 5 个窗口的元数据构成）。数据表明，G1、G2、G3 的 WASM 核心计算时间高度集中在 **11.0 ms – 11.7 ms** 之间，几乎不随餐次与算法变化发生大幅波动；
   - **推论**：在当前真实菜单规模下，WASM 核心执行耗时的 **~90%（约 10 ms）消耗在 41 KB JSON 字符串的零拷贝解析与 Catalog 内存对象构建上**，而真正的搜索算法执行耗时仅为 **~0.5 ms – 1.5 ms**；
   - 原生 CLI 宿主总耗时约为 64 ms – 67 ms，主要由 Windows 控制台子进程创建（`CreateProcess` 约 40 ms）、磁盘二进制动态加载与文件 I/O 构成。

### 6.5 内存检查与堆增长（Flat Tail）证据

- **测试方法与命令**：
  运行独立隔离检漏脚本 `node Resources/报告/T07b-反重力-固定候选性能与工程验证-证据-v3/check_memory.mjs`，加载生产 WASM 模块，分别对 G0–G3 典型场景连续执行 50 次完整规划请求，记录每 10 次的 WebAssembly 内存页数变化（1 页 = 64 KB）。
- **实测结果**：
  - G0-DP：初始 17 页（1,088 KB） $\to$ 第 1 次 47 页 $\to$ 第 10/20/30/40/50 次全部稳定在 **54 页（3,456 KB）**；
  - G0-BnB：初始 17 页 $\to$ 第 10/20/30/40/50 次全部稳定在 **74 页（4,736 KB）**；
  - G1-DP / G1-BnB：初始 17 页 $\to$ 第 10/20/30/40/50 次全部稳定在 **496 页（31,744 KB）**；
  - G2-DP / G2-BnB：初始 17 页 $\to$ 第 10/20/30/40/50 次全部稳定在 **497 页（31,808 KB）**；
  - G3-DP / G3-BnB：初始 17 页 $\to$ 第 10/20/30/40/50 次全部稳定在 **498 页（31,872 KB）**。
- **内存结论与工具局限性如实界定**：
  - 数据呈现标准 **平尾现象（Flat Tail）**：内存页数在首次请求完成堆分配到达峰值水位线后，后续 50 次高频调用中完全无单调递增，证明核心请求间的动态分配均在请求结束时完整归还或重置；
  - **重要工具边界声明**：本项基于 WASM 宿主内存页观测，仅能证明“在重复调用下无持续性单调泄漏（Monotonic Heap Growth）”，**不能推断 C++ 原生堆“绝对零泄漏”**。因当前宿主未配置 ASan / Valgrind / Dr.Memory 等侵入式内存检漏工具，不能从未支持检漏的工具推论零泄漏。
