## 3. 已核实的根因和复杂度边界

### 3.1 DP 状态上限约束保留层，未直接约束展开层

`planner.cpp:2032–2088` 先展开 `currentLayer × mealCandidates`，为每个终端转移计算 planKey，随后逐项扫描 `nextLayer` 做精确支配。到 **2097 行**才判断 `rawLayerCount > maxDpStates` 并桶化；桶查找（2117 行）和代表元插入排序（2137 行）又是线性扫描/二次过程。`maxDpStates=20000` 不是“最多评估/暂存 20000 个状态”。

令阶段 m 转移数 `R_m=L_(m-1) C_m`，未截断非支配状态数 `U_m≤R_m`，频次/比较成本为 F。该阶段精确扫描最坏 `O(R_m U_m F)`，桶查找和插入排序最坏 `O(U_m²)`，另有终端摘要的序列化/哈希成本。不能写成仅 `O(三餐 × maxDpStates)`。Vec 扩容旧缓冲与各阶段向量均由请求 Arena 持有至请求结束，`Clear()` 只清长度，故常驻的保留层数不等于峰值内存。

当前 cap256、DP20000 的早餐层为 46，午餐展开/非支配层为 8556（DP64/128/256 的早餐未截断对照均实际观察到同一值）。8556 未触及 20000，晚餐将尝试 **8556×186=1591416** 次转移，再进行同层支配。cap64 的晚餐转移上界也达 46×64×64=188416。上述是状态规模推导，不是已完成运行计数或精确耗时预测。

25 秒超时本身不能证明死循环、OOM 或每一毫秒的归属。本卡没有逐函数 profiler；源码的后置限额、二次扫描、低 K 对照的耗时下降共同支持搜索成本失控的诊断。未把超时当成某个未经测量的崩溃根因。

### 3.2 现有配置能给搜索一个小而明确的上界

三餐保留状态 K=32、当前候选 `(46,186,186)` 时，每层结束后最多保留 32 个状态，因此转移总数至多且本例实际为：

`46 + 32×186 + 32×186 = 11950`。

任一后继原始层最多 5952 个状态，仍会做二次扫描，故它是有限、已测的近似搜索规模，不是 32 个状态的实时硬限。若只采用每餐 cap256 的一般上界，三餐 DP 转移至多 `256+32×256+32×256=16640`，每个后继原始层至多 8192；此结论只针对搜索层，不包含菜单解析、候选生成及任意长标识符的成本。

另外，`RecurseMealOfferSubsets:865–909` 在达到候选保留限额后只跳过叶子的入池，外层窗口与组合递归仍继续统计/回溯，并非 A13 所述“彻底跳过后续窗口”。本次固定菜单只有 186 项，这没有构成主要风险；不能把 cap256 宣称为任意扩容菜单的全部枚举工作上界。

### 3.3 wallClockMs 目前不可作为兜底

`hasWallClockMs/wallClockMs` 只在 3022–3037 行解析赋值，所有算法搜索均没有读取计时器或更新 `anyWallClockCapHit=true` 的实现。WASM 仍为零 imports，当前没有宿主时钟接口。DP 也不消耗 `maxSearchNodes`，该字段的源码定义本来只覆盖 greedy/BnB，不能默默改作 DP 计数。

反例 `ignored_wall_complete`：单餐 DP、wallClockMs=1、maxSearchNodes=1，WASM 实际约 789.92 ms 后返回 `searchComplete=true`、186 转移、capsHit=[]；native 同一输入响应与 WASM 一致。三餐 DP32、wall1/nodes1 也仍评估 11950 转移。故双端当前是“同样忽略墙钟”，不是已具备可移植时间限制。不得通过把 null 改为 1 声称修复。本卡不擅改共享契约或 ABI。

### 3.4 共同 Arena 占用还有一个独立、可计算的下限

`json.cpp:180–185` 的 ParseString 对每个键/字符串值分配 `length-pos+1`，即从开引号之后到**整个输入末尾**的空间，而非当前字符串长度。对实际 98312 B 紧凑请求，3618 个字符串 token，逐项按源码公式求和为 **158133908 B（150.808 MiB）**，尚未计 JSON 节点、容器、候选和 DP；pretty 请求对应 **227789170 B**。

该数值由实际 token 起点独立复算，代码和原输入均可复核。greedy 的 161021952 B 与 DP32 的 168624128 B 实测也证实：大部分峰值是进入搜索前的共同开销，不能归咎于 DP 状态本身。最坏内存随字符串数×输入长度增长，通常可达二次量级。降低 K 无法清除此下限。这一普通解析器分配修复可交普通核心执行员定向处理，无需为此扩写 Sol 搜索算法。

## 4. 最小建议与隔离候选的含义

保留三算法与三餐功能，先把“覆盖问题”和“全天搜索规模”共同处理。隔离候选仅两行：

```diff
- maxMealCandidatesPerMeal: 64,
+ maxMealCandidatesPerMeal: 256,
- maxDpStates: 20000,
+ maxDpStates: meals.length === 3 ? 32 : 20000,
```

这使三餐 DP 使用已验证的小规模近似配置，单餐/两餐 DP 的原 K 不变，greedy/BnB 仍选原算法且不消耗此 K。cap256 恢复候选覆盖，未强迫任何窗口胜出。候选文件 SHA256 **ede3305e7673d727b389e790a90b12e026c2c1f49f005817e8dd7281fd88f38e**，41784 B；542 B unified patch 可审。本卡直接构造对应核心请求验证限额，不声称已完成该孤立 plan.ts 的完整前端编译/微信调用测试。

**这是供 P01 评估的缓解候选，不是性能达标补丁，也没有证明 32 为最优参数。** K16/32/64 的不同策略结果并非随 K 单调改善；本例 K32 primary 的偏差为 49 bp，economy 4400 分，taste 覆盖 5 类，但没有完整穷举的全局最优/质量损失证明。不能为了通过时延就直接禁用 DP、缩成单餐或改全天目标。

原有 T08 v1 的 50 ms/300 ms/768 页测试目标绑定旧 5 窗35 offer/每餐2项规模，不能直接冒称涵盖当前六窗口。即使仅作参考，当前 DP32 正式约 454 ms / 2573 页仍明显未满足；greedy 2457 页也超过该旧警戒值。新规模不能靠事后放宽阈值造通过。若要把性能闭合，优先定向修正上述解析器分配并重测；之后再按新测量决定 DP 是否需要无损支配索引/更早的有界近似处理，而不是现在泛化重构引擎。

本卡没有 C++ 生产补丁和新 native/WASM 产物，因为“当前真实三餐 DP 能有界返回”的最小处理已可用现有 K 配置证明；“生产性能达标”仍需后续整改，不能把前者说成后者。
