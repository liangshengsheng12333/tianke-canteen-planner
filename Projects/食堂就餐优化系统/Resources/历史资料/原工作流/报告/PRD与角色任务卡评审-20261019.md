## Standards：规范与岗位协作

### S01｜P2｜外部 Agent 的前置条件混入 Codex 专有模式名称

定位：[T03 第35行](../任务卡/T03-首批真实菜单.md:35)、[T04 第35行](../任务卡/T04-C++三算法.md:35)，同类条款存在于其他任务卡；对照 [PRD 第108行](../主PRD.md:108)。

主 PRD 的共同前置要求 P01 为真实 Default；复制到外部 Agent 任务卡后变成“接收窗口真实 Default”。反重力和 DSH 使用各自平台，材料没有说明它们具有 Codex 同名模式，也没有定义等价证明。

后果：外部 Agent 即使已经获得用户在 P01 的开工授权，也可能无法证明一个本平台不存在的模式；或自行文字声明 Default，留下无效证明。

建议：共同条件保留“用户在真实 P01 明确开工、P01 已退出 Plan”；Codex 接收窗口另核实其实际模式，外部平台记录原生执行状态及授权来源，不要求套用 Codex 模式名。同步主 PRD、总表、业务任务卡及后续外发包。

本轴共 1 项 P2；没有业务源码，无法作代码规范通过结论。岗位模型、身份、实读与未执行状态的区分目前没有发现实质矛盾。

### R02｜P2｜真机门禁被扩大成独立算法和界面工作的整体启动门禁

检查项：D1-3、D2-3、D4-3。

定位：[批准计划 第39行](../批准计划.md:39)、[批准计划 第116行](../批准计划.md:116)、[T04 第11行](../任务卡/T04-C++三算法.md:11)、[T05 第11行](../任务卡/T05-小程序与本地数据.md:11)。

批准计划要求优先验证真机链路，未通过不能宣称打通；并要求用户输入延迟时其余开发继续。当前 T04/T05 均以 T02 通过为完整前置。AppID、设备或预览权限延迟，即使契约和原生工具可用，也会卡住原生算法、存储和界面中的独立工作。

建议：区分“允许启动”和“可集成/可验收”。保留 T02 优先验证与最终真机硬门禁；T04 原生算法/穷举部分和 T05 页面/存储部分可在相应契约冻结后开展，桥接和正式集成部分依赖 T02。不要取消真机验收，也不要为这些部分虚报整体通过。

状态：待调整依赖；属于进度风险，不是技术路线已失败。

### R03｜P2｜未知营养的显示规则已有，但求解与评分策略仍未明确

检查项：D3-1、D3-3、D5-1、D5-2。

定位：[PRD 第38行](../主PRD.md:38)、[PRD 第52行](../主PRD.md:52)、[T01 第26行](../任务卡/T01-契约与营养配置.md:26)、[T04 第26行](../任务卡/T04-C++三算法.md:26)。

“未知不当零”是正确底线，但没有说明未知菜品是否进入自动推荐、只有部分营养素未知时如何比较，以及已吃未知食物后如何调整剩余餐次。仅统一 JSON 空值表达，仍可能让三个算法和界面作出不同决策。

建议：把以上行为列为 T01 必须关闭的决策表，至少覆盖全已知、单项未知、全部未知、实际摄入含未知四种情况。可选做法是自动营养优化仅使用信息足够的候选；未知食物允许记录并标明汇总不完整。具体选择须评估真实菜单覆盖，不能在本报告中直接定为新要求。

验收补充：同一含未知输入在三算法中采用同一资格/评分口径，界面不宣称已达到无法核实的目标。

状态：待 T01 冻结。现有“评分和字段后续冻结”已写明，本项不是要求现在填完全部参数，而是补齐待冻结行为。

### R04｜P2｜“随吃随调”的预算扣减与手工记录价格缺少统一口径

检查项：D3-3、D4-2、D5-1、D5-2。

定位：[PRD 第26—27行](../主PRD.md:26)、[PRD 第37—39行](../主PRD.md:37)、[PRD 第68—70行](../主PRD.md:68)、[T06 第26—27行](../任务卡/T06-全流程集成.md:26)。

预算可选、已吃锁定、允许补记菜单外食物，但未说明预算是全天总额还是本次剩余额；也未说明已吃金额如何扣减、补记价格未知如何处理、已经超支后是否仍生成后续餐次。营养超标“不自动取消后餐”不能自动推导为预算规则。

建议：在 T01 固定预算语义和实际消费字段，在 T05/T06 落实。例如明确全天预算、确认记录计入实际支出、改撤同步重算；价格未知则标明预算核算不完整。对余额为负时明确反馈及用户可采取的动作，不隐性追加预算。

验收补充：包含已吃消费、重复确认、改价/撤销、价格未知、已超预算五类输入，核对后续推荐与全天账目一致。

状态：待澄清业务口径，待 T01 写入契约。

### R05｜P2｜“今天、临时售罄、未吃餐次”的时间和状态边界不够清楚

检查项：D2-2、D3-3、D3-4、D4-2。

定位：[PRD 第25—28行](../主PRD.md:25)、[PRD 第35—40行](../主PRD.md:35)、[PRD 第70行](../主PRD.md:70)、[T05 第27—28行](../任务卡/T05-小程序与本地数据.md:27)。

数据中有日期餐次，但未说明跨日如何切换、临时售罄何时解除、已经过去但未确认的餐次是否继续推荐。当锁定的菜变为售罄，或菜单更新删除了被锁定菜品时，硬约束冲突也缺少具体后续动作。

后果：可能把昨天的售罄沿用到今天、晚间重算又推荐早餐，或让失效锁定长期造成无解。当前只能确认这些规则未说明，不能断言已经存在上述实现缺陷。

建议：补一张简明状态表，记录业务日期依据、餐次是否可手动补记/重算、售罄作用范围及解除入口，以及锁定失效后的提示和用户选择。具体截止时间不用凭空设定，可选择用户显式结束餐次的方式。

状态：待 T01/T05 明确；历史摄入快照不受菜单更新影响的既有规则保留。

### R06｜P2｜求解搜索限制有安排，但真机可用性的验收尺度缺失

检查项：D1-3、D3-1、D3-2、D5-2。

定位：[PRD 第38行](../主PRD.md:38)、[PRD 第79—82行](../主PRD.md:79)、[T07 第26—29行](../任务卡/T07-实验与一致性.md:26)、[T08 第24—29行](../任务卡/T08-真机与试用.md:24)。

文档要求比较耗时、状态/节点数和近似/超时，但没有菜单规模边界、单餐候选规模、手机响应目标及求解期间界面行为。T07 可以完整报告一个很慢的结果，T08 仍缺少可判定的流畅性标准；仅搜索节点限额不足以说明实际等待体验。

建议：T01 明确支持规模和正常/超限行为，T02 用最小真机测试提供初测，T07/T08 据此确定并验证响应与资源标准。至少定义加载反馈、输入变化后旧结果不得覆盖新请求，以及限额触发后如何返回已有结果或明确失败。具体时限需有初测依据，本报告不新设毫秒数。

状态：待补测量条件及通过标准；未对当前性能作结论。

### R07｜P2｜独立穷举的验证边界没有覆盖前置的一餐候选生成

检查项：D2-2、D3-1、D4-2。

定位：[PRD 第35行](../主PRD.md:35)、[PRD 第82行](../主PRD.md:82)、[DSH 角色卡 第8—9行](../角色卡/DSH-C++算法.md:8)、[T04 第27行](../任务卡/T04-C++三算法.md:27)、[T07 第26行](../任务卡/T07-实验与一致性.md:26)。

三个算法先使用合法单餐候选，再组合全天。已有规则要求穷举不复用被测剪枝逻辑，但未明确穷举是否只检查同一份候选表。如果候选生成漏掉半份米饭或合法套餐，三算法和穷举可能一起漏掉该方案，全天对照依然一致。

建议：补充两个验证层次：用人工可列全的极小原始菜单，独立核对单餐合法组合的完整性与计价；再对全天组合核对评分和最优性。候选截断或启发式预筛选也必须纳入近似标记，不能只标搜索阶段的截断。

状态：待补 T04/T07 验收条件；目前没有代码，本项是验证设计缺口。

## 非阻塞优化建议

1. **把重复规则收敛到一份执行约定。** 11 张任务卡反复复制历史输入、G3、模型与报告模板，后续容易出现一处更新多处陈旧。每卡保留负责人、具体输入、范围、产物、验收、依赖；共用条款引用单一文件。外部不可访问该文件时，在完整外发包中展开正文。
2. **补上营养计算配置的实施责任。** P01 组织、P09 核验已经明确；T01 文件归属表再指定谁实现公式、默认目标与适用性校验，以及前端和 C++ 各消费哪个结果。这样能避免反重力和 DSH 各写一套计算。
3. **增加一页页面/状态对应表。** 把建档、今日三餐、方案详情、记餐编辑、菜单/备份入口对应 R01—R09，附加载、空态、失败和恢复入口；不必扩成大量页面模板。
4. **展示准备提前积累。** 在实现三算法时同步留下原理图、反例、复杂度变量定义与真实实验数据，避免到 10/27 才准备全部讲解。PPT 本体仍按原约定由用户后续制作。
5. **面向对象表达作为答辩准备。** 可说明核心实体与算法类的职责、所有权及模块调用；课设原文未要求必须展示继承/多态，不能为凑概念强加设计或列为硬缺陷。
