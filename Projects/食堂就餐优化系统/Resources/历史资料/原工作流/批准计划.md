# 食堂就餐优化系统：模式一正式计划

## 1. 交付目标与范围

在 **2026 年 10 月 28 日汇报前**，完成可在红米 K90 Pro Max 上运行的微信小程序，支持个人日常使用和朋友小范围试用，围绕课程要求争取高分。

- 首批覆盖一个食堂内、能供应完整三餐的代表性窗口，随后通过菜单包扩充。
- 支持减脂、维持体重和规律训练偏好，提供“一套主推荐＋两套不同取舍的备选”。
- 全部开发、调试和测试由 AI 承担；用户提供菜单资料、注册账号并反馈真实使用体验。
- 交付源码、可运行小程序、C++ 原生实验程序、算法对比报告、营养依据和演示素材。
- **PPT 后续由用户使用反重力制作**，本轮保留所需截图和实验数据。
- 首版采用本地计算、本地保存，不接入付费模型服务，不建设服务器、云同步或社交系统。公开上线与 iPhone 适配不作为本轮通过条件。

## 2. 产品行为与技术结构

采用**原生微信小程序 TypeScript＋WXML/WXSS，以及 C++17 算法核心**。C++ 编译为 WebAssembly 接入小程序，同时提供调用同一核心的本机命令行程序。

### 日常使用

- 建立身体档案、活动水平、目标和口味偏好；BMI 自动计算，体脂率选填。
- 首页先展示今天三餐、购买窗口和价格，再展示能量及主要营养素进度。
- 每餐默认在一个窗口买齐；用户也能先选窗口，再让系统搭配。
- 自选菜按单道价格计算；套餐按真实套餐价格、选菜数量及米饭包含规则计算。
- **米饭可半份，其他菜按实际整份售卖**；不同餐次分别使用对应的供应窗口与菜单。
- 换菜优先在同窗口替换单道菜；无法满足要求时，再展示调整整餐或换窗口的方案。
- 推荐菜单与实际摄入分别保存。一键确认后才计入已吃记录，支持修改、撤销和补记饮料、零食及其他食物。
- 调整推荐时锁定已吃内容，只重算尚未吃的餐次。摄入超出计划时说明偏差，不自动取消后续餐次。

### 数据与接口

统一使用版本化 JSON：`Profile`、`MenuCatalog`、`PlanRequest`、`PlanResult`、`MealLog`。金额使用整数分，份量使用实际售卖单位。

- `PlanRequest` 包含菜单版本、营养目标、可选预算、偏好、已吃记录及锁定的窗口或菜品。
- `PlanResult` 返回推荐组合、营养与价格汇总、差异说明、未满足目标和求解状态。
- C++ 提供统一规划入口，原生程序与 WASM 使用相同输入和评分规则；明确返回结果的内存释放方式。
- 菜单包记录窗口、餐次、菜品、套餐规则、价格、营养来源和估算依据。导入先校验，失败保留原菜单；历史记录保留当时的数据快照。
- 个人支持临时标记售罄、本地数据导出和恢复。身体档案与记录默认留在设备。

**最早技术检查点**：先验证一个 C++ 算法通过 WASM 在真实小程序中运行，并与原生程序输出一致。未通过前，不将完整界面开发视为核心链路已打通。

## 3. 营养规则与三个核心算法

### 营养计算

以成年学生日常饮食管理为适用范围，提供带依据的估算结果。

- 使用 Mifflin–St Jeor 公式估算静息能量消耗，结合活动水平估算每日消耗；清楚区分估算与实测。[原始研究](https://pubmed.ncbi.nlm.nih.gov/2305711/)
- 维持模式以估算消耗为起点。减脂模式采用**减少估算消耗 10%、缺口最多 300 kcal/日**作为产品初始估算参数，明确其属于待实际反馈校正的产品默认值。
- 自动估算设置成人适用范围和低摄入拦截；体重过轻、孕哺期及需要疾病饮食管理的情况不自动生成减脂目标。手动填写目标同样经过适用性检查。[NIH 工具适用范围](https://www.niddk.nih.gov/health-information/weight-management/body-weight-planner)
- 展示能量、蛋白质、脂肪和碳水，并考虑食物类别与多样性。规律训练偏好采用单独的蛋白质配置，不增加训练课程或补剂推荐。[WHO 健康膳食原则](https://www.who.int/news-room/fact-sheets/detail/healthy-diet)、[运动营养依据](https://link.springer.com/article/10.1186/s12970-017-0177-8)
- 菜名、价格和照片用于建库；菜品营养按参考食物、配方及假定份量估算，展示依据。缺失营养数据标为未知，不按零处理。
- 营养公式、参数、单位和适用条件集中配置，P09 核对来源与计算后才能纳入通过版本。

### C++ 算法

三个算法解决同一套三餐组合问题，使用相同菜单、约束和评分函数：

| 算法 | 职责 |
|---|---|
| 贪心 | 快速生成基础组合，作为对比基线 |
| 动态规划 | 按餐次组合候选方案，复用等价状态 |
| 分支限界 | 利用界限剪枝搜索，小规模下用于核对最优结果 |

- 先生成各窗口内合法的一餐，再组合全天方案；明确区分不可违反的购买规则与可解释的营养偏差。
- 评分优先比较营养目标满足程度，再比较口味和价格；主推荐、经济备选与口味备选使用明确区分的排序策略。
- 预算内无法达到营养目标时，说明冲突，同时给出预算内方案和超预算备选；超预算方案须醒目标明。
- 比较结果质量、耗时、状态或搜索节点数量。小规模用完整穷举作独立参照；设置搜索上限的结果标注近似或超时状态。
- 报告各算法的时间、空间复杂度及适用规模。BMI 和代谢公式不计入三个核心算法。

## 4. 精简岗位与模式一初始化

工作区为 **`D:\项目\cpp`**。当前尚无代码或岗位窗口，后续使用真实独立聊天记录身份，不以子代理代替岗位。

| 角色 | 职责及配置 |
|---|---|
| P00｜初始化 | 编写主 PRD、角色卡、任务卡和总表；完成报到与交接后结束初始化职责 |
| P01｜总指挥 | 统一接口、调度反重力与 DSH、管理集成版本和验收；承担总指挥职责 |
| P09｜独立验收 | 独立复核整合版本、算法和交付证据；请求 `gpt-6-luna / high` |
| 反重力 Agent | 主做小程序、交互、本地数据和 WASM 接入；3.8 Flash 用于日常开发，Gemini 4 用于复杂问题 |
| DSH Agent | 主做 C++ 算法、原生实验、正确性及性能验证；使用 DeepSeek V4.1 Flash |

P00、P01 沿用用户配置的 Codex 默认模型；所有角色分别记录请求配置与可核实的实际配置。不另设 P11，不连接网页顾问。

初始化顺序：

1. 用户批准执行计划并实际退出 Plan 后，创建独立 P00。
2. P00 输出主 PRD 等材料，交用户确认。
3. PRD 确认后创建 P01、P09，并准备反重力与 DSH 初始化包，由用户接入外部 Agent。
4. 全员实际读卡、报到、待命；记录身份、职责、文件范围与缺失项。
5. P00 向 P01 交接。用户在 P01 明确开工后，按依赖派发开发任务。

先冻结共用接口，再划分文件负责人；反重力与 DSH 分开修改各自模块，共用接口变更由 P01 协调。
